# 邀请邮件与确认入组真实联调

沿用 PostgreSQL 17.11、Redis 7.4.12、RabbitMQ 4.4.0、Linux Celery prefork 和本地 SMTP 收件器，扩展既有 `mail_smoke.py` 的单条业务场景。两个账号都通过真实收到的验证码邮件完成注册，没有直接种入用户、成员或岗位记录。

## 已通过的流程

1. 邀请人登录并补全昵称，创建剧组，取得该剧组管理员身份。
2. 创建发给另一邮箱的邀请，接口返回 202 和 `pending_dispatch`；相同待接受邀请重复创建返回 409。
3. Outbox 将邀请任务交给真实 Worker；收件器收到邀请邮件，任务类型和事件类型均为 `invitation_email`，执行次数为 1。邀请凭证只从邮件链接提取，创建响应和任务引用中均无明文凭证。
4. 邀请人尝试接受发给另一邮箱的邀请，返回 400 `INVITATION_INVALID`。
5. 受邀人用自己的验证码邮件注册、登录；未补全昵称时接受邀请返回 403 `PROFILE_INCOMPLETE`。
6. 受邀人补全昵称后明确接受，获得正常成员身份；重复接受同一凭证返回相同结果。
7. 直接查询 PostgreSQL：剧组共 2 位成员，受邀账号只有 1 条成员关系，成功接受审计只有 1 条。新成员岗位为空，未自动获得管理员／导演等身份；调用邀请接口返回 403。
8. 另创建一条尚未发送的邀请并撤销；数据库任务变为 `cancelled`，Outbox 为 `failed`，dispatcher 没有可投递任务，收信总数保持为 3（两封验证码、一封邀请）。

上述流程和原有验证码重复消息去重一并通过。本轮未发现需要修改邀请业务代码的问题；新增的是对正式 API、仓储、队列和消费者的真实链路验证。

## 复现与环境调整

按[消息与邮件联调](mail-integration.md)启动独立依赖，在 `backend` 执行：

```powershell
.\.venv\Scripts\python.exe scripts/mail_smoke.py
```

每次创建新测试库，只运行这一条组合场景；不运行前端全量测试，不发往外部邮箱，不读取或修改 `.env`，不调用模型。Worker 和回环 SMTP 接收器在结束时自动关闭，依赖按需停止。

本机从 Windows 挂载目录恢复 RabbitMQ 数据及加载 Erlang 运行包较慢。本轮将已校验的原始包一次解压到 WSL 项目专属执行缓存，队列数据也使用 WSL 原生目录；原目录保留，私有配置记录 `linux_data_dir`。缓存丢失时从项目内原始包恢复，不重装系统环境。临时缓存不作为正式部署持久存储。

## 验证边界

这次验证 HTTP 层的完整邀请入组路径及上述拒绝／重放条件；没有覆盖真实邮箱服务、邀请页面的完整浏览器操作、多人并发接受与撤销、过期等待、离组后重新邀请和 Broker／Worker 崩溃。相关规则已有单元测试，但仍不能据此宣称真实并发、故障恢复或高 QPS 验收通过。
