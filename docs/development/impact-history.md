# 变更检查与问题观察历史

本批增加显式检查批次、持久问题及状态变化历史，迁移头`0024_impact_history`。迁移仅离线验证，未执行真实PostgreSQL迁移。

## 检查与实时清单

普通刷新仍只读实时业务事实，不自动写问题表。用户显式“检查并记录当前类别”时，系统完整检查所选类别的已录入关联，保存当时发现的问题及变化；处理和发布规则仍由原业务接口实时校验。记录不存在或状态为已不再待处理，均不代表当前筹备全部就绪。

当前为同步检查，一次最多1000个待处理目标，不接入新的RabbitMQ任务。检查不接收分页、目标ID或人工完成状态；超过上限409 `CHANGE_CHECK_TOO_LARGE`，不执行部分更新。失败只保留既有失败审计路径，不保存成功批次、不将未检查项清除。前端仍可查看实时分页清单。

检查在同一剧组协调事务中完成，取得一次数据库观察时间，读取完整实时集合、记录目标及已消失目标的真实依据。权限与业务变更使用同一协调锁，检查期间不提交混合新旧依据；任一步失败整体回滚。上限限制本批处理规模，尚未验证大数据或高并发性能。

## 记录语义

本批以“剧组＋类别＋具体资料／安排版本ID”作为唯一目标组，不按每个原因建立另一条问题。目标同时存在多项原因时保存在同一快照；原因或来源依据变化记录为更新。此处目标ID已经是拆解、分镜、排期或通告的具体版本ID，不使用可空版本字段作唯一键。

| 变化 | 行为 |
|---|---|
| 首次检查发现 | 新建`open`记录，保存首次发现时间及当时依据 |
| 持续存在且依据不变 | 更新最近检查时间／批次，不重复生成变化记录，不增加语义锁版本 |
| 持续存在但依据变化 | 递增版本，追加`updated`；不推断未观察到的解决或复发 |
| 新检查已不再列出 | 回读原目标事实，保存具体原因和引用，标记`resolved`并追加变化 |
| 曾不再列出后再次发现 | 复用原问题ID，增加复发次数，清除当前解决结论并追加`reopened`，原历史保留 |

首次发现时间是**系统实际成功检查到的时间**，不冒充问题真实发生时间。两次检查之间短暂出现又消失的变化可能没有记录；只有观察到解决后再出现，才计作复发。更换为另一份具体业务版本会形成不同目标记录。

“不再待处理”区分实际依据：固定来源回到工作稿、人工复核仍适用、排期／通告撤回、被新版本替代、拍摄及转场已结束、既有复核条件已解除。时间结束不描述为已修复排期；不因读过通知、知悉或点击查看而解决问题。来源复核依据保留实际复核记录ID、工作稿ID／序号及目标锁，其他记录保留当前指针、状态和复核原因代码。

## 数据表及事务

- `impact_check_runs`：成功检查类别、检查者及其当时入组身份、观察时间、发现／更新／解决／复发／未解决计数，并保存请求键及内容摘要。
- `impact_issues`：稳定问题ID、所属剧组与目标组、`open/resolved`、最近报告快照、最新实际检查依据、首次／最近检查时间、解决依据、复发次数和锁版本。同组同类别同目标唯一；四种目标使用类别约束及同剧组复合外键，禁止跨组引用。
- `impact_issue_transitions`：只追加的`detected/updated/resolved/reopened`记录，保存前后快照、依据、检查批次及时间；同一问题／批次最多一条转换，同组外键约束问题与检查批次。

问题快照中的标题与原因是当时最后一次报告的内容，解决后不会伪装为当前业务详情。历史接口按冻结快照返回，后续剧本重命名或换稿不改写旧事件。

检查批次、问题更新、转换历史及成功审计同事务提交。状态或结果依据变化才递增问题锁；无变化检查也保留成功批次，便于区分“没有新变化”和“没有执行检查”。已经解决且当前未重新出现的旧问题不重复重检或生成关闭记录。

## 权限、幂等与接口

检查与记录读取沿用该类别的完整读取权限。检查只能记录系统实际计算的事实，不授予审核资料、修改排期、发送通告或替人确认的权限。当前类别无权读取时，在计数、历史或幂等重放前拒绝访问；原成员重入后不得继承旧检查请求。

路径位于`/api/v1/crews/{crew_id}/change-issues/{category}`，类别仍为四种既有类别。

| 方法与路径 | 输入／返回 |
|---|---|
| POST `/checks` | CSRF、UUID幂等键、空JSON `{}`；成功201返回原检查ID、时间与各项计数 |
| GET `/records` | `status=all/open/resolved`及分页，每页1—20；返回问题记录和该类别最近成功检查 |
| GET `/records/{issue_id}/history` | 分页，每页1—20；返回该问题及冻结的转换历史 |

读限流120次／分钟，显式检查10次／分钟，均按IP与账号。异组、异类别或未知问题404，无类别读取权403，无效输入422，数据库失败脱敏503。

幂等键按剧组与用户唯一，摘要包含类别、剧组和完整输入。同键重试返回原成功批次，不重新计算、不重复记历史；类别不同409，入组身份改变409。重放结果仍基于原观察时间，即使之后业务已有新变化也不宣称执行了新检查。

## 页面

统一清单内增加“检查与问题记录”。打开历史只执行GET；显式检查成功后展示计数并读取历史。可筛选记录状态，查看首次／最近观察时间、复发次数及变化时间线，解决原因使用业务表述。

结果未知保留原请求键手动重试，并暂时锁定类别切换、处理跳转和关闭，避免丢失待确认请求。已知拒绝释放界面并刷新当前剧组权限／事实；普通读取失败隐藏旧私有记录。检查不会发通知、改变发布安排、取消预约或扣减库存。

## 与完整设计的差异及验证

本批落地持久问题及观察历史，按目标组聚合原因；未按完整设计逐个触发关系建立独立问题，也未将来源复核改为依赖问题ID。原来源复核仍绑定资料及工作稿，历史检查通过引用保存相应依据。

`impact_check_states`、源业务事务内标记待检查／Outbox、后台自动检查、逐事件捕获、通知去重尚未接入；因此界面只显示最近**成功记录**时间，不声称业务变更后历史状态立即同步。正式发布实时校验与原同步失效规则保持有效。

定向验证覆盖发现／更新／解决／复发、无变化去重、撤回／替代／结束区分、真实来源复核引用、完整类别扫描、超限或失败不关闭、原请求重放、当前权限及入组身份、只读历史、接口和离线SQL约束。前端覆盖显式记录、原键重试、重复点击、类别锁定、筛选及时间线。真实数据库并发、浏览器视觉和容量验收待完成。

已进一步在真实 PostgreSQL 17.11 验证发现、无变化去重、来源复核后关闭及历史读取，并修正 `resolution_basis` 的 JSONB 空值映射。完整链路及验证边界见 [PostgreSQL 联调说明](postgres-integration.md)。后台自动检查暂缓，继续采用同步失效规则、实时清单及用户显式记录。
