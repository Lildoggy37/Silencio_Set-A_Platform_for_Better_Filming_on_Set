# Silencio Set · 核心表字段与约束

版本：D0.22  
状态：已确认五批数据及四批核心流程，已同步认证、资源、计划及Diane执行约束；具体接口和实现细节待补。

## 1. 公共约定

使用PostgreSQL，表与字段采用英文名称，文档采用中文说明。下表为适用的公共字段，各表按职责选用；不要求所有关联表重复添加全部字段。

| 字段 | 类型 | 约束与说明 |
|---|---|---|
| `id` | UUID | 主键，由服务端生成 |
| `crew_id` | UUID | 剧组业务记录必填；用户、固定岗位及权限目录等全局数据除外 |
| `created_at` | TIMESTAMPTZ | 创建时由服务端记录 |
| `updated_at` | TIMESTAMPTZ | 可变记录修改时由服务端更新 |
| `lock_version` | INTEGER | 需要防止并发覆盖的可变记录启用，初值1，每次修改递增 |

时间按带时区时间戳存储，页面按Asia/Shanghai展示。`lock_version`用于并发更新检查，不等同于剧本、计划等业务版本号。

不统一引入软删除字段。成员退出、任务取消使用明确业务状态，历史版本和审计按各自规则保留。必填文本去除首尾空白后不可为空，字段长度继承需求数据定义；引用有效性和同剧组约束同时通过数据库及业务服务检查。

## 2. 用户与注册验证

### 2.1 用户表 `users`

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | UUID | 主键 |
| `email` | VARCHAR(254) | 必填，保存用户输入的邮箱展示形式 |
| `email_normalized` | VARCHAR(254) | 必填、唯一，用于查找及重复注册判断 |
| `password_hash` | TEXT | 必填，仅存密码散列，不保存明文密码 |
| `display_name` | VARCHAR(30) | 注册后待补全时可空；完成资料时去除首尾空白后1—30字，不要求唯一 |
| `profile_completed_at` | TIMESTAMPTZ | 未补全时为空，首次成功补全时记录 |
| `lock_version` | INTEGER | 初值1，个人资料修改时检查递增 |
| `email_verified_at` | TIMESTAMPTZ | 有效账号必填，表示注册邮箱验证成功时间 |
| `status` | VARCHAR(20) | 必填，取`active`、`disabled` |
| `created_at`、`updated_at` | TIMESTAMPTZ | 必填 |

已确认采用“邮箱验证码验证注册，邮箱＋密码日常登录”。只有验证成功才创建有效账号，唯一约束处理并发重复注册。邮箱规范化统一去除首尾空白并进行大小写归一化，不删除点号或`+`后缀；展示值与查询值分开保存。

本次用户补充要求将昵称从注册必填调整为首次登录后补充：未补全账号可登录，但不得进入剧组业务。`profile_completed`由完成时间及有效昵称共同判断，不存独立可矛盾的布尔值；完成时间非空时昵称必须有效，完成后不能清空。资料保存与完成时间同事务提交，版本用于防止覆盖。创建或接受剧组前检查资料已完成，以当前昵称初始化剧组内显示名；之后个人昵称变更不自动覆盖剧组显示名或历史快照。头像、真实姓名、学校等不新增为必填。

第一批流程审阅已确认密码使用Argon2id散列，采用服务端Cookie会话及CSRF防护，详见《04_关键流程与异常处理》；具体散列参数、密码规则、会话有效期及重置范围后续细化，不自动扩展全部账号恢复功能。

### 2.2 Redis邮箱验证记录

键结构示意：`email_verification:{purpose}:{email_digest}`。保存验证码摘要、验证请求标识、有效期及失败次数；邮箱摘要不作为匿名化保证，相关记录仍按认证数据保护。

要求如下：

- 不同验证用途隔离，验证码不写入普通日志。
- 重发后旧验证码失效，验证成功后原子消费，防止重复使用。
- 邮箱与IP分别限流；失败次数到达限制后拒绝继续尝试。
- 邮件异步发送前检查请求是否仍有效，避免队列延迟发送旧验证码。
- 验证码摘要用于校验，后台发送使用下节短期加密载荷，不把明文验证码作为长期任务结果保存。

有效期、重发间隔及次数后续补定；验证码消费与账号写入通过短期注册凭证及下表的数据库消费记录衔接，不假设Redis和PostgreSQL共同提交。

### 2.2.1 短期邮件敏感载荷

Redis键`mail_payload:{payload_id}`保存不透明随机标识、用途、当前验证请求或邀请引用、收件人绑定、加密载荷、加密密钥版本和算法需要的随机／完整性参数，以及创建、过期时间。采用成熟认证加密实现，不自行发明算法；真实解密密钥独立于Redis和数据库保管，不进入仓库。该记录仍属敏感资料，仅后端发送进程按用途读取，不因密文而对用户公开。

载荷只含发送所需短期验证码或邀请凭证及必要模板值，TTL不超过对应验证或邀请有效期，可按发送窗口更短设置。任务和Outbox仅保存`payload_id`及业务引用，不保存明文或解密密钥。缺失、过期或解密失败停止发送，不能从校验摘要生成原文；邮件被服务明确接受后可清理，结果不明按受控处理保留到TTL，不无限延长敏感内容寿命。

先建立有效业务请求与短期载荷，再提交任务及Outbox；跨Redis与PostgreSQL不假设原子性。数据库失败留下的载荷按TTL清理，任务有记录而载荷缺失时失败，不伪称成功；邀请数据库记录可保留但用户需按规则重新申请发送。Worker发送前检查引用当前有效、未撤销及仍匹配，发送中发生重发不能收回在途邮件，验证端始终拒绝失效旧码或旧凭证。具体加密库、TTL、密钥轮换和加载配置待实施验证。

### 2.3 注册凭证消费表 `registration_receipts`

| 字段 | 类型 | 约束与用途 |
|---|---|---|
| `id` | UUID | 主键 |
| `token_digest` | TEXT | 必填且唯一，关联验证成功后签发的随机注册凭证，不存原始凭证 |
| `email_normalized` | VARCHAR(254) | 必填，与被验证邮箱及新账号一致 |
| `user_id` | UUID | 必填，引用本次成功创建的用户 |
| `token_expires_at` | TIMESTAMPTZ | 必填，凭证原有效期，用于重试校验 |
| `consumed_at` | TIMESTAMPTZ | 必填，实际提交成功的消费时间 |

本表无剧组归属，与用户创建在同一PostgreSQL事务保存；唯一约束防止同一凭证重复创建账号。Redis中的短期凭证绑定邮箱并设有效期，数据库提交前不先删除其唯一重试依据；提交后的清理失败不撤销账号。同一有效凭证重试不能覆盖已设置密码，也不自动获得登录会话。

服务端会话保存在Redis，至少关联随机会话标识、用户、有效期及必要的CSRF状态，不把原始密码放入会话。Cookie属性、会话失效及验证流程见《04_关键流程与异常处理》。

## 3. 剧组与成员

### 3.1 剧组表 `crews`

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | UUID | 主键 |
| `name` | VARCHAR(50) | 必填，1—50字 |
| `project_name` | VARCHAR(100) | 必填，1—100字 |
| `description` | VARCHAR(1000) | 可空 |
| `created_by` | UUID | 必填，引用`users.id` |
| `created_at`、`updated_at` | TIMESTAMPTZ | 必填 |

首期一个剧组对应一个项目，项目名称保存在剧组表，不额外建立只有名称的项目表。不同剧组允许同名，以标识区分。创建者只用于记录来源，不自动成为永久权限持有者。

### 3.2 成员表 `crew_members`

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | UUID | 主键 |
| `crew_id` | UUID | 必填，引用剧组 |
| `user_id` | UUID | 必填，引用用户 |
| `display_name` | VARCHAR(30) | 必填，剧组内显示名称 |
| `status` | VARCHAR(20) | 必填，取`active`、`left`、`removed` |
| `joined_at` | TIMESTAMPTZ | 必填，当前或最近一次加入时间 |
| `ended_at` | TIMESTAMPTZ | 在组时为空；退出或移除时必填 |
| `lock_version` | INTEGER | 初值1，成员状态、岗位或例外权限修改时统一检查并递增 |
| `created_at`、`updated_at` | TIMESTAMPTZ | 必填 |

设置`UNIQUE(crew_id, user_id)`，同一用户在同一剧组保留一条成员关系。退出、移除和重新加入的事件通过审计保留，历史业务仍引用原成员标识。

重新加入恢复原成员关系，但需重新授予岗位和权限，不自动恢复旧授权。创建剧组、创建首名成员及授予管理员身份在同一事务中完成；移除或取消最后一名管理员受业务规则限制。

成员记录作为岗位及例外授权集合的并发控制锚点；修改这些关联记录须在同一事务中检查并递增成员版本。最后一名管理员保护在剧组协调锁下检查，避免并发撤权各自判断通过。

### 3.3 剧组邀请表 `crew_invitations`

本批接口审阅确认管理员按邮箱邀请、受邀者登录后接受；沿用FR-01的7天有效期、可撤销及接受后失效规则。

| 字段 | 类型 | 约束 |
|---|---|---|
| `id`、`crew_id` | UUID | 主键、所属剧组 |
| `email_normalized` | VARCHAR(254) | 必填，与接受者已验证邮箱匹配 |
| `token_digest` | TEXT | 唯一，保存不可预测邀请凭证的摘要，不存原始凭证 |
| `invited_by_member_id` | UUID | 必填，邀请人 |
| `status` | VARCHAR(20) | `pending`、`accepted`、`revoked`、`expired` |
| `expires_at` | TIMESTAMPTZ | 创建时起7天；校验实际时间，不依赖过期清理任务 |
| `accepted_by_user_id`、`accepted_at` | UUID、TIMESTAMPTZ | 接受成功时记录，否则为空 |
| `lock_version` | INTEGER | 初值1，接受、撤销及状态更新时检查递增 |
| `created_at`、`updated_at` | TIMESTAMPTZ | 必填 |

同剧组、同邮箱最多一条`pending`邀请；已过期但尚未清理的记录在重发事务中先处理失效。接受邀请与建立或恢复成员关系在同一事务完成，重复接受不生成第二条成员关系。邀请不直接授予岗位；重新加入仍须重新授权。邀请邮件通过待投递记录发送，凭证不进入普通日志；安全投递细节随后续邮件配置细化。

## 4. 岗位与权限

首期使用固定岗位及权限目录，不提供自定义岗位编辑器。

| 表 | 字段及类型 | 约束与用途 |
|---|---|---|
| `roles` | `code` VARCHAR(32)，`name` VARCHAR(30) | 代码为主键，名称必填；如`director`、`producer`，实际目录与需求角色对齐 |
| `permissions` | `code` VARCHAR(100)，`description` VARCHAR(500) | 代码为主键；完整默认目录及判定见《10_权限矩阵与接口授权》第2—5节 |
| `role_permissions` | `role_code`、`permission_code`，类型与被引用代码一致 | 组合主键，分别引用岗位及权限，定义默认授权 |
| `member_roles` | `crew_id` UUID，`member_id` UUID，`role_code` VARCHAR(32) | 必填；同一成员与岗位组合唯一，成员必须属于该剧组 |
| `member_permission_overrides` | `crew_id` UUID，`member_id` UUID，`permission_code` VARCHAR(100)，`effect` VARCHAR(5) | 必填；成员与权限组合唯一，`effect`为`allow`或`deny`，成员属于该剧组 |

有效权限按岗位默认权限并集计算，再应用成员明确允许或拒绝，最后检查业务对象及状态限制。例如拥有资源管理权限不等于可以代替任何资源负责人批准预约。

退出或移除成员时撤销当前授权，历史操作由审计记录保留。多岗位、覆盖授权及管理员保护规则不能因前端隐藏按钮而省略后端验证。

已确认固定岗位、默认业务权限与管理员可授予范围见[权限矩阵](10_权限矩阵与接口授权.md)。基础成员能力参与默认权限计算，明确拒绝优先于允许，最终仍检查对象关系。管理员可授予预定义业务权限，不要求自己具有业务执行权；组织管理权限只通过`admin`岗位变更，不允许普通例外授权伪造或部分覆盖。创建者无永久超级权限。资源负责人指定时检查其审批权限，经办另检查资源范围；范围关联字段后续补齐。

## 5. 任务与提交

### 5.1 任务表 `tasks`

| 字段 | 类型 | 约束 |
|---|---|---|
| `id`、`crew_id` | UUID | 主键、所属剧组 |
| `title` | VARCHAR(100) | 必填，1—100字 |
| `description` | VARCHAR(3000) | 可空 |
| `owner_member_id` | UUID | 必填，一名负责人；不设置单列唯一，允许同一成员负责多项任务 |
| `reviewer_member_id` | UUID | 必填，一名确认人 |
| `created_by_member_id` | UUID | 必填，发布人 |
| `scene_id` | UUID | 可空，引用稳定场戏对象，场戏表在下一批细化 |
| `due_at` | TIMESTAMPTZ | 必填，创建时晚于当前时间；保留逾期任务原值 |
| `status` | VARCHAR(20) | 必填，取`pending`、`in_progress`、`pending_review`、`completed`、`cancelled` |
| `cancel_reason` | VARCHAR(500) | 取消时必填，1—500字 |
| `lock_version` | INTEGER | 必填，初值1，修改递增 |
| `created_at`、`updated_at` | TIMESTAMPTZ | 必填 |

负责人、确认人和发布人必须属于任务剧组；发布及新指派时检查在组状态和相应权限，历史引用不因退出而删除。状态转换由业务服务校验，更新时比较`lock_version`；版本不匹配返回冲突，不静默覆盖。

协作人使用`task_collaborators`，核心字段为`crew_id`、`task_id`、`member_id`，均为UUID且必填；任务与成员组合唯一，引用必须属于同一剧组。不使用逗号分隔ID保存人员列表。

### 5.2 任务提交表 `task_submissions`

| 字段 | 类型 | 约束 |
|---|---|---|
| `id`、`crew_id` | UUID | 主键、所属剧组 |
| `task_id` | UUID | 必填，引用同剧组任务 |
| `submission_no` | INTEGER | 正整数，同一任务内递增，`UNIQUE(task_id, submission_no)` |
| `submitted_by` | UUID | 必填，提交成员标识 |
| `completion_note` | VARCHAR(2000) | 必填，1—2000字 |
| `review_status` | VARCHAR(20) | 必填，取`pending`、`accepted`、`rejected` |
| `reviewed_by` | UUID | 审核后必填，未审核为空 |
| `review_note` | VARCHAR(500) | 退回时必填，1—500字 |
| `submitted_at` | TIMESTAMPTZ | 必填 |
| `reviewed_at` | TIMESTAMPTZ | 审核后必填，不早于提交时间 |

提交与任务进入待确认须一致完成；验收通过后任务进入已完成，退回则恢复进行中。再次提交创建新记录，不覆盖旧结果和退回原因。具体并发提交、验收与取消的协调方式在任务事务设计中明确。

## 6. 文件表 `files`

统一记录剧本、勘景照片和通告单PDF的元数据，文件本体保存在本地私有目录。

| 字段 | 类型 | 约束与用途 |
|---|---|---|
| `id`、`crew_id` | UUID | 主键、所属剧组 |
| `uploaded_by` | UUID | 必填，上传者对应的剧组成员；系统生成文件记录触发成员 |
| `original_name` | VARCHAR(255) | 必填，原文件名，仅供展示 |
| `storage_key` | TEXT | 必填、唯一，服务端生成的相对存储标识 |
| `detected_type` | VARCHAR(100) | 文件可用时必填，记录服务端检查得到的类型 |
| `size_bytes` | BIGINT | 文件可用时大于0，按业务用途检查上限 |
| `checksum` | VARCHAR(64) | 文件可用时必填，文件摘要，不设置全局唯一 |
| `status` | VARCHAR(20) | 必填，取`uploading`、`available`、`failed` |
| `created_at` | TIMESTAMPTZ | 必填 |

请求不能自行指定服务器路径，原文件名不能直接作为存储路径。访问时检查剧组与关联业务权限，不允许仅凭文件ID下载。文件被业务记录引用时不能直接删除。

剧本使用已确认的20MB限制，按20×1024×1024字节检查；照片和导出文件的大小及类型限制后续确定，不自动沿用剧本限制。上传及生成失败时的临时文件清理在文件流程设计中细化。

## 7. 剧本与版本

### 7.1 剧本表 `scripts`

| 字段 | 类型 | 约束 |
|---|---|---|
| `id`、`crew_id` | UUID | 主键、所属剧组 |
| `title` | VARCHAR(100) | 必填，1—100字 |
| `current_version_id` | UUID | 可空，只能引用本剧本已确认的工作版本 |
| `created_by` | UUID | 必填，创建成员标识 |
| `created_at`、`updated_at` | TIMESTAMPTZ | 必填 |

剧本是稳定业务对象，当前工作版本指向其某次已确认提交。没有确认版本时允许为空，不将正在解析或失败内容作为正式正文。

接口审阅补充`lock_version INTEGER NOT NULL`，初值1，剧本信息及工作版本变更时检查递增。正文确认与工作版本切换独立。

### 7.2 剧本版本表 `script_versions`

| 字段 | 类型 | 约束 |
|---|---|---|
| `id`、`crew_id`、`script_id` | UUID | 主键、所属剧组及剧本 |
| `version_no` | INTEGER | 正整数，同一剧本内递增，`UNIQUE(script_id, version_no)` |
| `input_type` | VARCHAR(20) | 必填，取`docx`、`pdf`、`txt`、`paste` |
| `source_file_id` | UUID | 文件输入时必填，引用同剧组文件；粘贴时为空 |
| `version_note` | VARCHAR(1000) | 可空 |
| `status` | VARCHAR(20) | 必填，取`parsing`、`pending_check`、`confirmed`、`failed` |
| `confirmed_by`、`confirmed_at` | UUID、TIMESTAMPTZ | 已确认时必填；其余状态为空 |

解析失败记录可保留用于排查，但不构成需求中的有效版本，也不能成为工作版本。确认前允许修正提取正文，确认后正文不原地覆盖；后续修改形成新版本。解析任务状态、错误说明与该记录关联，具体错误字段在异常处理设计中细化。

核心字段为`id`、`crew_id`、`script_id`，均为UUID且必填；另记录创建者及创建、修改时间。场戏标识表示同一业务场戏，展示编号及内容保存到修订记录中。

场戏展示编号在同一拆解版本内唯一，不能跨所有历史修订设置简单全局唯一。接口审阅补齐下述拆解对象。

### 9.2.1 拆解版本表 `scene_breakdowns`

| 字段 | 类型 | 约束 |
|---|---|---|
| `id`、`crew_id`、`script_version_id` | UUID | 主键、所属剧组及已确认来源版本 |
| `version_no` | INTEGER | 同一来源剧本版本内递增且唯一 |
| `review_status` | VARCHAR(20) | 草稿、待审核、已确认、已否决，枚举与场戏修订一致 |
| `lock_version` | INTEGER | 初值1，条目及状态变化时递增 |
| `created_by`、`created_at`、`updated_at` | UUID、TIMESTAMPTZ、TIMESTAMPTZ | 必填 |
| `reviewed_by`、`reviewed_at` | UUID、TIMESTAMPTZ | 审核后记录 |

场戏修订补充必填`breakdown_id UUID`，来源剧本版本须与拆解一致；设置`UNIQUE(breakdown_id, scene_number)`及`UNIQUE(breakdown_id, scene_id)`。条目修改、送审及整份审核在所属拆解记录上协调，内容变化递增拆解版本；修改已有修订还检查其自身版本。整份审核与所属修订状态一致。已确认拆解修改时创建新拆解及新修订，查询须明确拆解版本。

审核退回后为`rejected`，不可直接编辑；有编辑权限者显式`reopen`，检查版本后将整份及所属修订恢复`draft`并递增对应版本，保留旧审核历史。`pending_review`禁止编辑，`confirmed`禁止重新打开。审核、条目编辑及重新打开锁定同一拆解协调，不出现已确认整体中的可编辑修订。

审核历史表`scene_breakdown_reviews`保存UUID字段`id`、`crew_id`、`breakdown_id`、`reviewed_by`，`decision`取`accept`或`reject`，`review_note VARCHAR(500)`退回时必填，`reviewed_lock_version INTEGER`记录所审核版本，`reviewed_at TIMESTAMPTZ`记录时间，`content_snapshot JSONB`保存该次被审核的场戏及来源、原文范围。审核记录与状态同事务保存，不随重新编辑覆盖。快照为受同等权限保护的业务数据，不写入普通日志。

### 9.3 原文及内容关联

`scene_source_refs`保存`crew_id`、`scene_revision_id`及起止段落编号；范围必须存在于修订所引用的剧本版本，起始编号不大于结束编号，提交审核时具有有效原文依据。

人物及资源需求采用关联记录，保留人物名称、需求类型、名称及数量；资源需求允许未绑定具体设备，表示仍未落实。其完整字段随人物及资源设计细化，不在修订正文中使用逗号分隔ID代替关联。

新剧本版本中的场戏是否对应旧场戏，由用户确认；不能仅因场戏编号相同就自动认定身份一致。已确认并被正式计划引用的修订不得随新稿原地改变。

## 11. 人员档期表 `member_availability`

接口审阅补充集合控制表`member_availability_sets`：`crew_id UUID`、`member_id UUID`构成唯一成员范围，`lock_version INTEGER NOT NULL`初值1，另记录`updated_at TIMESTAMPTZ`。该记录作为本人整段替换档期的锁定及版本锚点，无档期条目时也能协调并发。首次创建通过唯一约束协调；查询不存在的集合返回初始版本，写入时在同一事务创建并锁定后校验。

替换时先按统一顺序取得剧组协调锁及集合记录锁，检查集合版本，保留范围外部分并拆分跨边界旧区间，再写入范围内新集合并递增集合版本。删除条目也必须递增集合版本，单条区间版本不能代替集合版本。实际档期变化后检查受影响的已发布计划并发出复核提醒。

| 字段 | 类型 | 约束 |
|---|---|---|
| `id`、`crew_id` | UUID | 主键、所属剧组 |
| `member_id` | UUID | 必填，引用同剧组成员 |
| `starts_at`、`ends_at` | TIMESTAMPTZ | 必填，结束晚于开始，可跨日 |
| `availability` | VARCHAR(20) | 必填，取`available`、`unavailable` |
| `lock_version` | INTEGER | 必填，用于并发修改检查 |
| `created_at`、`updated_at` | TIMESTAMPTZ | 必填 |

成员仅维护本人档期，管理员和Diane不能代改。同一成员的已登记区间统一禁止重叠，修改时显式调整已有区间，不采用可用与不可用相互覆盖的优先级规则。区间按起始包含、结束不包含处理，相邻边界不算重叠。

未登记时间不生成未知记录。检查拍摄时段时，与不可用区间重叠为冲突；被可用区间完全覆盖为可用；没有明确冲突但存在未登记部分为未完全确认。转场准备时间按需求BR-05参与相关成员的时间检查。

## 12. 资源与场地

### 12.1 资源表 `resources`

| 字段 | 类型 | 约束 |

| `unit` | VARCHAR(10) | 必填，台、件、处等 |
| `total_quantity` | INTEGER | 可复用资源必填且至少1；耗材为空 |

### 12.2 场地及勘景照片

`location_details`补充场地地址、进入方式和拍摄限制，只关联`location`类型资源；同一资源最多一条详情。`location_photos`关联场地与同剧组文件，并记录照片说明，同一场地可有多张照片。

`location_photos`明确保存`id`、`crew_id`、`location_resource_id`、`file_id`、`created_by`等UUID，`description VARCHAR(500)`可空，`created_at TIMESTAMPTZ`必填；同场地与文件关联唯一，每个场地最多20张有效关联。关联时锁定资源、检查版本及当前数量，避免并发越限，不将路径存进描述，不默认AI图片分析。

勘景文件接受JPEG、PNG、静态WebP，单张不超过10×1024×1024字节，解码像素不超过25000000；拒绝SVG、动图、HEIC及损坏文件。按方向信息规范展示后生成清除EXIF定位等元数据的文件，原始临时上传不作为可访问正式原件保留；处理成功才置为available。记录规范化文件的实际格式、大小、摘要及宽高，`files`可补充`width_px`、`height_px`正整数，非图片可空。像素、文件及关联数量均为已确认设计初值，不是处理性能承诺；解码内存、时限和磁盘仍需实测。场地地址等详情长度仍随其完整契约细化。

接口审阅确认场地详情及照片关联修改检查并递增所属`resources.lock_version`，不另建可独立覆盖的关联集合版本。

### 12.3 资源范围授权表 `resource_scope_grants`

| 字段 | 类型 | 约束 |
|---|---|---|
| `crew_id`、`resource_id`、`member_id` | UUID | 必填，资源及成员属于同一剧组 |
| `permission_code` | VARCHAR(100) | 必填，只取`resource.manage`、`reservation.review`、`resource.checkout`、`resource.return`、`stock.manage` |
| `granted_by`、`created_at` | UUID、TIMESTAMPTZ | 实际管理员成员及授权时间 |

设置`UNIQUE(resource_id, member_id, permission_code)`。范围记录不替代有效权限：先计算岗位及例外允许／拒绝，再检查资源范围；明确拒绝优先。制片默认`resource.manage`覆盖本组资料维护，不因此获得全组审批、借还或库存经办权。其他成员持资源业务代码仍需具体资源范围；预约审批额外要求当前资源负责人。类型不适用的范围授权拒绝，不以授予库存代码为设备生成耗材流水。

管理员明确维护授权，检查其组织权限，不要求管理员自身具有对应业务操作权。修改范围按剧组协调锁及资源版本控制，与审批和负责人交接协调，记录授权差异审计。负责人交接先验证新人权限及范围，撤销旧负责人的该资源审批范围，不因旧页面或Agent已排队保留批准能力。成员离组清除当前范围记录并保留审计，重新入组不恢复。

`plan_preflight_checks`保存`id UUID`、`crew_id UUID`、`plan_version_id UUID`、`checked_by UUID`、`checked_lock_version INTEGER`、`expected_current_published_version_id UUID可空`、`checked_data_revision TEXT唯一`、`data_snapshot JSONB`、`unknown_items JSONB`、`created_at TIMESTAMPTZ`及`expires_at TIMESTAMPTZ`。标记由服务端生成，不接受前端自行声明；绑定实际检查成员、剧组、草稿和来源。具体有效期在运行配置确定，过期须重检。

本阶段通告导出格式为PDF；DOCX、PDF剧本输入范围不变。导出与下载绑定确定通告版本，不用旧PDF替代失败的新版本导出。

### 19.3 通告接收人集合与发布快照

| 表 | 字段与约束 |
|---|---|
| `call_sheet_draft_recipients` | `crew_id`、`call_sheet_version_id`、`member_id`均UUID，同组且`UNIQUE(call_sheet_version_id, member_id)`；保存审核前的选择集合，不另存与计划可矛盾的可修改必选标记 |
| `call_sheet_published_recipients` | `crew_id`、`call_sheet_version_id`、`member_id`均UUID，组合唯一；`published_at TIMESTAMPTZ`及`required_at_publish BOOLEAN`必填，作为该版发布时接收范围快照，不随当前成员变化覆盖 |

默认接收人是来源计划在该拍摄日场次参与成员的去重并集，属于必选；可增加其他在组成员。后端从来源重新计算必选，不信任前端可选标记。更改集合须检查并递增通告`lock_version`，待审核不可改，已审核变更使状态恢复草稿、旧审核失效；内容与接收集合一并重审。`call_sheet_reviews`补充`recipient_member_ids_snapshot JSONB`，保存被审核集合，不随重新选择变化。

详细接口确认`call_sheet_reviews.review_note`为`VARCHAR(500)`，退回必填且不可空白；每次通过／退回持久关联审核请求幂等结果，重复请求返回同一`review_id`，不另建审核记录。

发布事务重检所有接收人在组、必选覆盖、来源和所审核集合一致性，任何不匹配返回明确冲突，不静默跳过。快照、通告状态、当前指针、审计及待通知事件同事务提交；通知接收记录依据快照幂等生成。原成员离组保留历史快照回执但失去访问权。

原接收人投递失败按原通知补投，不产生新通告或清除回执。增加原未选择成员必须创建新通告版本并重审，不对已发布快照原地加人；新版本需包含仍在组的必选人员和经重新确认的可选人员，不盲目复制已离组对象。成员查看按有效接收关系或业务权限判断，持链接不授予访问。

通告不反向静默改写计划。计划新版发布后，相关已发布通告来源过期标为`review_required`，内容相同也需复核，可复制形成新版；场次移日时两天均复核。原日期不再拍摄时旧通告标为`withdrawn`，不再作为当前有效安排并通知原接收成员。新通告发布后旧版标为`superseded`，新版本验证来源及审核后为`valid`。

旧正文、PDF和确认记录保留，新版本重新通知确认。网页与旧链接读取有效性并提示当前安排；过期PDF不能当作新版结果返回。导出失败不影响网页发布。有效状态的转换及重复发布处理与正式业务事务协调，不能仅由通知任务决定。

复制计划不能重复创建资源预约，替换旧计划不能擅自取消预约；涉及资源变化仍由资源模块按权限及规则处理。

## 23. 操作提案表 `agent_action_proposals`

| 字段 | 类型 | 约束与用途 |
|---|---|---|
| `id`、`crew_id`、`run_id` | UUID | 主键、所属剧组及执行 |
| `action_type` | VARCHAR(50) | 必填，限定为批量创建任务、调整计划、申请资源预约 |
| `target_refs` | JSONB | 必填，目标对象、标识及来源版本，新增对象时记录必要关联 |
| `proposed_changes` | JSONB | 必填，按具体操作结构校验，不能接受任意字段或任意工具名 |
| `impact_summary` | JSONB | 必填，受影响成员、安排、冲突及必要提示 |
| `status` | VARCHAR(30) | 必填，取`pending_confirmation`、`confirmed`、`rejected`、`invalidated`、`executing`、`completed`、`partially_completed`、`failed`；confirmed为已确认待调度，executing仅用于实际执行 |
| `confirmed_by`、`confirmed_at` | UUID、TIMESTAMPTZ | 确认后记录实际成员及时间，由后端写入 |
| `execution_key` | TEXT | 必填且唯一，关联正式业务执行，重复确认不能另建执行标识 |
| `result_refs` | JSONB | 执行后记录实际产生或修改的业务记录及结果，不以模型声明代替 |

审批时检查确认人权限，执行时重检权限、目标版本与约束；模型不能自行填写有效审批结果。旧提案失效后重新检查并生成待确认提案，不能直接修改已确认内容继续执行。正式业务变更、执行标识、实际结果及成功审计共同提交；重复确认、Worker重试及LangGraph恢复先检查该结果，已执行不重复修改。

接口审阅补充提案`lock_version INTEGER NOT NULL`，初值1，状态变化时递增；人工决定提交所见提案版本并检查，内容调整创建新提案而不是替换已确认内容。重复决定先通过幂等记录定位原结果，不因原请求成功后的版本递增而误报冲突。

详细契约补充`decision_note VARCHAR(500)`可空、`decided_by UUID`及`decided_at TIMESTAMPTZ`决定后必填，记录接受及拒绝的实际主体与时间；原`confirmed_by/confirmed_at`仅接受时填写。决定仅允许从`pending_confirmation`进行，决定、状态版本及幂等结果同事务保存，接受还同事务创建唯一恢复任务和Outbox，返回其ID。`confirmed`与run的调度状态及消息待投递状态各有职责，不表示业务已完成；实际Worker取得执行权才进入`executing`，业务结果仍与正式变更及成功审计共同提交。

部分完成只用于如实表达已发生结果，不意味着允许任意拆分原本应原子完成的业务操作；各操作的原子性、失败及补偿边界留待事务设计确定。

### 23.1 提案审阅分发表 `proposal_reviewers`

`crew_id`、`proposal_id`、`member_id`、`assigned_by`为UUID，`assigned_at`为TIMESTAMPTZ，必填；设置`UNIQUE(proposal_id, member_id)`并检查同组。`assigned_by`记录实际提案创建成员，不由模型任意指定。集合更新检查并递增提案`lock_version`，仅`pending_confirmation`允许；决定和集合修改锁定同一提案，保留分发变更审计，决定后不得修改。

创建者可选仍在组且对该提案动作、全部必要目标具有实际权限与责任的确认人，分发表只赋予提案必要信息的审阅入口，不赋予业务权。创建者本就可查看自己的提案；他人须在分发集合且仍有相应业务权才可查看和决定。任何确认仍须实际动作权限及当前对象检查；多名候选人为任一人一次有效决定，不是会签。离组或撤权后访问和决定失效，不因旧分发表永久授权，重新加入不恢复旧分发入口。

独立入口仅返回变更、必要依据、影响、版本和经过权限过滤的结果引用，不返回私有对话和其他工具输出。分发通知若发送只含最小入口信息，读取时重检；批次提案的必要动作不能由无完整权限的候选人部分批准。

## 25. 后台任务表 `background_jobs`

| 字段 | 类型 | 约束与用途 |
|---|---|---|
| `id` | UUID | 主键，也是消息中引用的任务标识 |
| `crew_id` | UUID | 剧组业务任务必填，注册邮件尚无剧组时可空；不得因此跳过用途授权 |

| `status` | VARCHAR(30) | 必填，取`pending_dispatch`、`queued`、`running`、`retry_wait`、`succeeded`、`failed`、`cancelled` |
| `idempotency_key` | TEXT | 必填，按任务类型及明确业务范围防重复，唯一范围在任务接口中确定 |
| `attempt_count` | INTEGER | 非负整数，记录已开始的尝试次数 |
| `execution_token` | UUID | 执行取得后记录本次随机执行标识，接手生成新值；终态保留最后值供定位，不代表仍有效 |
| `worker_id` | VARCHAR(200) | 当前或最近执行者标识，仅作运行定位，不作授权凭证 |
| `lease_expires_at` | TIMESTAMPTZ | 执行租约截止；未执行或阶段已释放时可空 |
| `heartbeat_at` | TIMESTAMPTZ | 最近成功续租时间，可空 |
| `scheduled_at`、`started_at`、`finished_at` | TIMESTAMPTZ | 对应调度及执行事件发生时记录 |
| `result_ref`、`error_summary` | JSONB、文本 | 可空，结果引用与脱敏失败摘要 |
| `created_at`、`updated_at` | TIMESTAMPTZ | 必填 |

RabbitMQ消息携带任务ID，PostgreSQL保存正式任务及业务状态；Celery返回成功不能单独作为业务已完成的证明。重试、投递回执及执行回写的状态协调在任务流程中设计，不能因消息先后到达将已完成状态回退为排队。

Agent执行一次等待确认可以对应前后多个后台任务，后台任务完成不必等于整次Agent执行完成。审批等待释放Worker，继续执行另行调度。取消只表达实际取消结果，不能隐藏已经完成的业务变更。

Worker以数据库条件更新检查可执行状态、现有租约及当前时间，原子取得新token和租约并增加尝试次数，不因收到消息直接执行业务。续租、结果和终态写回须匹配当前token及有效执行权；到期后不可用旧token复活租约，接手者重新生成token，旧Worker迟到结果拒绝。使用数据库时间判断，租约、心跳和接手参数随后续配置确定。

正式业务写入前在事务中校验当前执行权及稳定业务执行键，业务结果与任务记录按既定事务协调，防止只拦任务终态却允许旧Worker重复改业务。租约不保证外部SMTP或模型只调用一次，外部结果不明仍先核实。人工等待持久化后完成当前后台阶段并释放租约，不长期心跳；恢复使用新后台任务关联原run和业务执行标识，不重建等价业务操作。

|---|---|
| `id`、`crew_id` | UUID，主键及所属剧组 |
| `issue_type` | 固定枚举：`source_review_required`、`resource_unfulfilled`、`related_object_unavailable`、`availability_review_required`、`call_sheet_review_required` |
| 触发引用 | `source_type`固定对象类型、`source_id UUID`及必要来源版本 |
| 受影响引用 | `target_type`固定对象类型、`target_id UUID`及`target_version_id UUID可空`，必须同组 |
| `status` | `open`或`resolved`，不以通知已读改变 |
| `first_detected_at`、`last_checked_at` | TIMESTAMPTZ，记录首次发现及最近实际检查 |
| `resolved_at`、`resolution_basis` | 解决时记录时间及JSONB依据，含检查或人工复核对象和版本；未解决可空 |
| `lock_version` | INTEGER，初值1，状态和检查结果变化递增 |

同组、类型、触发引用、受影响对象及版本形成唯一逻辑问题键；版本为空须采用明确的空值等价唯一约束，不能依赖普通nullable组合键避免重复。持续问题更新同一记录，不重复制造提醒；解决后同一问题复发恢复open、清除当前解决结论，历史转换与依据留审计。若受影响的是不同业务版本则分别记录，不覆盖历史。

| 触发 | 当前问题与解除条件 |
|---|---|
| 剧本工作稿切换 | 来源待复核；授权人员核对关联并记录当前工作稿下结论，后续再换稿不能沿用旧复核 |
| 需求未关联资源 | 资源未落实；补关联并重新检查准备情况，存在资源ID不等于已预约落实 |
| 停用或成员离组 | 关联对象不可用；调整关联或恢复对象后重检 |
| 本人档期变化 | 档期待复核；处理冲突或未知后重检，不回滚本人真实档期 |
| 来源计划变化 | 通告待复核或撤回；执行既有新版本审核发布或撤回规则 |

来源人工复核保留`source_review_records`：UUID标识、剧组、目标及固定来源版本、当前工作剧本版本、实际复核者，另记录结论说明、复核时间和依据快照。按对应资料审核权限检查，版本变化后旧结论不再解除当前问题；复核不改写旧修订或已发布安排。

详细字段补充`issue_id UUID`、`reviewed_issue_lock_version INTEGER`、`conclusion VARCHAR(20)`（still_applicable或needs_revision）、`review_note VARCHAR(1000)`必填1—1000字、`request_key TEXT`，按剧组、复核者及请求键唯一识别，幂等内容及返回结果持久保存。记录与当前问题转换同事务完成；仅来源问题支持人工复核，needs_revision保持open，still_applicable重检后只解除该项，不自动确认目标或变更来源。

### 29.2 检查状态 `impact_check_states`

按剧组和受影响对象及版本保存`requested_revision INTEGER`、`checked_revision INTEGER`、`check_status`（`pending`、`checking`、`current`、`failed`）、最近检查时间及脱敏失败类别，目标范围唯一。源业务变更在事务中标记关联目标待检查并保存Outbox；对尚需发现的关联以对应剧组检查范围标记pending，避免未发现目标时误显示全部就绪。

后台只对其取得的检查修订写入结果；若期间又有变化，旧结果不能将新修订标为current。检查成功才更新checked_revision和对应问题，失败显示待检查／失败，不显示无问题。通告失效等已有同步规则仍在来源变更事务内完成，异步问题分析不能延迟正式失效。正式审批发布始终实时校验，不依赖问题表是否已生成；只检查已录入关联，不宣称覆盖外部安排。
