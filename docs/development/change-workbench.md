# 变更待处理清单

本批增加总览中的统一只读清单和处理导航。复用现有业务表、来源适用性复核和正式安排标记，不新增问题状态表，不执行新的数据库迁移；迁移头仍为`0023_source_reviews`。

## 入口与范围

总览按当前权限显示“变更待处理清单”，打开才读取数据。按类别分页，每页1—20项；不返回未授权类别的数量或标题。

| 类别 | 读取权限 | 清单内容 |
|---|---|---|
| 场戏来源 | `script.read + scene.read` | 固定剧本来源不同于工作稿，且没有当前有效“仍适用”复核的拆解 |
| 分镜来源 | `script.read + storyboard.read` | 同上，分别使用该分镜的来源复核 |
| 正式排期 | `plan.read_all`或`plan.edit` | 当前正式版本有复核标记，且仍有未结束的场次或转场 |
| 每日通告 | `call_sheet.edit/review/publish`之一 | 当前发布通告待复核，或来源计划已替代／待复核，且当天来源场次尚未结束 |

组织管理员身份、本人相关安排读取权不自动取得全组清单。资料列表包含未复核的历史版本、旧来源草稿和未设置工作稿的情况，不将这些历史资料都定义为当前拍摄必用品；已判定需修订的资料继续显示。已复核仍适用项移出清单，但原内容及复核记录保留。

正式安排仅按当前指针聚合，已撤回或被替代的通告不计入待处理；已结束安排不继续占据清单。通告拍摄日按`Asia/Shanghai`的场次开始日期归属，跨夜场次及其转场尚未结束时仍显示，不因过零点提前消失。

## 数据一致性

来源 SQL 筛选与原来源复核读取共用依据字段：目标锁、固定原稿、工作稿ID和工作稿变更序号，并以最新复核记录为准；未确认资料不继承曾经的来源结论。计划与通告读取既有`review_reasons`、`validity_status`及当前正式指针，不维护另一份完成状态。

读取在剧组协调事务内取得一次数据库观察时间，计数、分页和未结束时段判断均使用该时间。来源复核按当前页批量加载，不逐条查询；正文、复核依据、用户邮箱等不放入聚合清单。普通查询不改变复核结论、发布状态、通知已读或成员知悉，也不发送提醒。

未设置问题“一键完成”或“忽略”操作：来源问题由有权审核者记录适用性或基于工作稿修订；排期及通告按原流程重新检查、审核、发布或撤回，完成后清单读取相应事实。清单为空只表示当前类别没有已识别项，不替代正式发布预检或证明全部筹备就绪。

## 接口

GET `/api/v1/crews/{crew_id}/change-issues/{category}?page=1&page_size=20`。

`category`为`breakdowns/storyboards/plans/call_sheets`。成功200返回类别、当前可读类别、`observed_at`、分页记录、总数及页码。每条含目标ID、类别、父对象ID、导航来源ID、标题、状态与原因代码；通告另含通告集合ID和真实当前正式排期版本ID。

复用会话、已完善昵称和当前成员检查；读取限流按IP及账号各120次／分钟。无类别权限403，未知类别或越界分页422，依赖故障返回脱敏503，不伪装为空清单。接口只读，不提供POST代签或直接消除问题的接口。

另补GET `/api/v1/crews/{crew_id}/shooting-plans/{plan_id}`返回准确计划元数据。完整读取权限可查同组目标；只有本人相关权限时，仍须是当前安排参与人且入组身份匹配。未知／无关目标404，不通过列表分页推断当前正式版本。

## 处理导航

- 资料项可直接打开固定历史资料及来源复核。需修订或缺工作稿时另有剧本入口，定位该剧本的当前工作稿；只读人员的按钮按权限显示为查看，不暗示具有编辑权。
- 排期项定位计划及对应正式版本。当前指针由计划详情读取，目标不在列表第一页时仍能正确显示。
- 通告项有完整排期权限时，定位当前正式排期（无当前版本时查看原来源）并选中受影响通告版本，便于继续处理。只有通告权限者可查看真实通告正文并联系制片，不制造或开放一个无权读取的完整排期。
- 切换剧组清除定位状态，数据、缓存键与所有读取始终按剧组及用户隔离。

清单手动刷新，已有业务写入沿用剧组查询失效机制更新状态；读取失败隐藏缓存的旧私有信息。原来的四个一级导航和通告嵌套于排期的设计保持一致。

## 验证与剩余边界

定向验证覆盖角色／能力边界、来源依据与SQL关联、时段及跨夜判断、批量和分页、读取无业务写入、故障与HTTP约束、来源／排期／通告精确定位，以及旧页面相关回归。未进行真实PostgreSQL联调、浏览器视觉验收或容量测试。

本批完成统一只读工作台。设计中的`impact_issues/impact_check_states`持久问题池、异步检查状态、独立问题解决／复发审计和提醒去重尚未实现；现有业务审计、来源复核历史及发布回执继续保留。资源和档期问题仅汇总其已产生的正式排期标记，实时具体冲突仍以原预检为准。

后续`0024_impact_history`已增加显式检查及持久观察历史，见[问题历史说明](impact-history.md)。本批原先未持久化的表述为当时阶段记录；后台自动检查及逐事件捕获仍待接入。
