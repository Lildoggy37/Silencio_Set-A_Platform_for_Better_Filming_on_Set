# 成员邀请与邀请邮件

## 2. 契约与权限

以下接口均位于`/api/v1`，沿用Cookie、来源、CSRF、16KiB实际JSON字节限制、禁缓存与脱敏错误。写接口每IP/用户窗口10次，读取120次。普通成员不能查询剧组邀请邮箱或原始凭证。

| 接口 | 输入与结果 |
|---|---|
| `POST /crews/{crew_id}/invitations` | 管理员输入`email`；成功202返回`invitation`摘要与`delivery_status=pending_dispatch`，不表示送达，不返回链接凭证或邮件任务ID |
| `GET /crews/{crew_id}/invitations` | 管理员分页查询，可选`status=pending/accepted/revoked/expired`；摘要含ID、受邀邮箱、状态、创建/到期时间及版本 |
| `POST /crews/{crew_id}/invitations/{id}/revoke` | 管理员提交`expected_lock_version`；仅未过期、待接受邀请可撤销，成功200返回新状态和版本 |
| `POST /invitations/accept` | 已登录且昵称完成的用户提交`token`；成功200返回`crew_id`、本人`membership`及`accepted=true`，不自动授予岗位 |

分页默认20、最多100条，页码1—100000。创建和管理在剧组协调锁后重新检查`member.invite`；撤销同时校验成员身份、对象归属和邀请版本。错误包括`INVITATION_PENDING`、`MEMBER_ALREADY_ACTIVE`、`VERSION_CONFLICT`及`INVITATION_NOT_PENDING`。

受邀者只允许接受与本人当前已验证规范化邮箱一致的邀请。无效、过期、撤销、错误邮箱或邀请人已无有效管理权限统一返回`INVITATION_INVALID`，不提供邀请详情。邀请码不能自报身份、岗位或接受成功状态。

## 3. 持久化与并发

- 凭证使用256位随机值；数据库只保存SHA-256摘要与邮箱绑定。邀请自数据库创建时间起7天有效，判断实际到期时间，不依赖定时清理。查询时将已到期`pending`显示为`expired`。
- 同剧组同邮箱最多一条`pending`，通过部分唯一索引保证。仍有效时重复创建返回冲突，不再发信；过期后在同一协调事务内结束旧记录，再创建新凭证。需要提前重新邀请时先明确撤销旧邀请。
- 创建邀请、保存邮件任务、Outbox及成功审计在同一PostgreSQL事务提交，提交前不报告202。已在组的邮箱不创建邀请；不公开该邮箱在全平台的注册状态。
- 接受先锁定并检查当前账号，再取得剧组协调锁并重读邀请状态，随后建立或恢复成员关系、标记接受、停止尚未执行的邮件并记录审计。接受与撤销串行协调，不能根据等待前的旧状态执行。
- 相同用户重复接受可恢复已提交结果，但必须仍在有效期内且原成员关系当前在组；不创建第二条成员关系，不借旧的已接受凭证恢复退出或移除的成员。
- 重新加入复用原成员标识，采用当前昵称并递增成员版本，清除旧岗位和例外授权；新加入默认没有岗位。已在组成员不会因接受重复邀请被清空原岗位。
- 邀请人失去当前有效成员/管理员身份或账号被停用后，未接受邀请不再允许发送或接受。此规则落实延迟操作重查权限，重新授权后仍需检查原邀请状态和有效期；未来账号停用等写入须参与剧组权限协调。

成功审计共同提交；拒绝/失败另行记录必要标识与原因，不记录凭证或邮件原文，审计再次失败只保留脱敏运行错误。创建和撤销没有独立幂等回执：响应未知时先查列表；不能宣称网络故障下邮件严格只发一次。

## 4. 邮件与敏感载荷

邀请凭证和收件地址只在内存及Redis中的Fernet认证密文出现，使用独立`MAIL_PAYLOAD_KEY`；最多15分钟TTL，与7天邀请有效期分开。载荷绑定用途、邀请ID、剧组、收件人、摘要及发送期限，不能被验证码消费器混用。

Redis准备与数据库不假装是跨库事务：Redis失败回滚数据库；数据库提交失败或结果不明时不盲删密文，孤立载荷按TTL清理。后台记录只保存不透明引用与必要摘要，RabbitMQ只投递任务UUID；长期任务结果、普通日志和API响应不保存原始凭证。

Outbox只认固定的`verification_email`、`invitation_email`类型，并检查事件类型与任务类型一致；不把其他文档/Agent任务当邮件投递。邀请任务名为`silencio.mail.send_invitation`，消费者仅条件领取邀请类型任务。投递预算、Worker租约、执行token与未知SMTP结果不重放规则沿用[邮件链路说明](mail-flow.md)。

发送前重新检查邀请为待接受、未过期、邮箱及凭证摘要匹配，且邀请人仍有权限；接受或撤销同时取消尚未执行的邮件。已在途邮件无法收回，但邀请接受端继续拒绝失效凭证。SMTP接受不等于收件人收到；发送后数据库结果保存失败仍可能处于未知状态。

邮件模板固定，仅生成`INVITATION_PUBLIC_ORIGIN/#invitation=<credential>`链接；不接受任意跳转地址或模板。前端域必须是配置的认证允许来源，不带路径、用户名、密码、查询或fragment；明文HTTP仅允许回环地址。默认`http://127.0.0.1:5173`。

## 5. 前端与恢复

管理员在成员页打开邀请管理，输入邮箱后只显示“已受理、尚不能确认送达”；撤销先显示收件邮箱和影响，再明确确认。结果未知或版本冲突会保留输入并阻止再次操作，必须先刷新列表。邀请凭证不在管理员列表显示。

受邀链接使用fragment，前端读取后立即从地址栏移除，只留在组件内存，不写URL查询、DOM、localStorage、sessionStorage或查询缓存。先完成登录和昵称，再显示当前邮箱并等待用户明确接受；不会在打开链接、注册完成或补昵称后自动加入。切换账号保留内存邀请，加入结果未知允许用户明确重试同一凭证恢复结果。刷新会丢失邀请进度，需要重新打开邮件；“稍后处理”不撤销后台邀请。

接受成功后清除凭证并重新请求对应剧组详情，再进入工作台。所有页面和API仍由服务器检查当前成员和对象权限，前端入口不替代授权。
