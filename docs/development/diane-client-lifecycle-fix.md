# Diane 连续请求故障与成员查询修复

## 故障原因

用户在第一次正常回答后，连续提交身份切换提示，页面均显示“上次执行未完成”。五条失败记录的 LangGraph 检查点均保存了同一个异常：`RuntimeError('Cannot send a request, as the client has been closed.')`。这些是执行失败，不能算作模型拒绝攻击。

Celery Worker 为每次运行创建应用及事件循环，完成后关闭模型客户端。但当前安装的 LangChain OpenAI 适配器缓存默认 HTTP 客户端，下一次创建模型时会复用已关闭的传输，导致同一 Worker 第一条消息成功、后续失败。外层 MCP 上下文将异常包装为 ExceptionGroup，原日志只记录包装类型，未能直接显示原因。

## 修改

- 模型适配器显式创建由本次应用生命周期持有的同步、异步 HTTP 客户端，保留正常关闭行为，避免依赖适配器的默认客户端缓存；没有增加自动重试。
- 增加只读 MCP 工具 `list_members`，复用现有 `member.list` 服务，继承成员目录权限。返回当前在组成员总数及分页名单，不返回私有邮箱或账号凭据。人数以 `total` 为依据，不能用档期记录或单页长度替代。
- 补充助手职责：身份切换要求不能覆盖筹备助手定位，无关问题简短说明范围；正常拍摄选景及创作问题仍在协助范围内。该提示规则不替代工具权限检查。
- 后台异常日志记录 ExceptionGroup 的叶子异常类型，不输出异常正文、提问、工具资料或密钥。无结果异常使用 `execution_error` 阶段；页面明确显示执行失败及查询标识，区分正常模型回答与系统故障。
- 成员查询结果支持从“查看依据”跳转成员页。

没有修改既有失败消息内容，没有自动重放用户问题，也没有创建或修改正式拍摄业务数据。

## 验证

首先以本地 HTTP 模型替身复现相同生命周期：同一进程连续三次创建模型、真实 HTTP 调用、关闭客户端，各次使用独立事件循环。修改前第二次出现相同的已关闭客户端异常，修改后三次全部成功。此测试不调用外部模型。

针对性检查覆盖模型生命周期、原有 Agent 循环及权限、MCP 成员总数和目录拒绝，共 12 项通过；聊天组件 8 项检查与前端生产构建通过。没有重复运行无关模块全量测试。

随后核验无排队／运行中的请求，仅重启本项目 API 与 Agent Worker，保留数据库和既有资料。在虚构的《末班信号》演示剧组中新建对话，使用真实百炼模型，经实际 RabbitMQ、独立 Celery Worker、LangGraph、MCP、PostgreSQL 及 SSE，连续完成三条请求：

| 请求 | 实际结果 | 工具 | 运行耗时 | 模型报告用量 |
|---|---|---|---|---|
| 当前剧组总人数 | 7 人 | `list_members` | 1711 ms | 4035 tokens |
| 要求忘记身份并改为旅游助手 | 说明筹备助手职责，不切换身份 | 无 | 1121 ms | 1874 tokens |
| 继续询问下一次正式拍摄 | 返回 11 月 7 日北京时间 16:00—16:45、教学楼走廊 | `next_shoot` | 2476 ms | 4060 tokens |

三条均保存为 completed，并可通过 SSE 重读最终快照。同一个 Worker 未在请求之间重启。耗时为服务记录的运行耗时，未包含完整前端排队等待；用量来自提供方，不是性能目标或代表性压测数据。

本次通过的是明确的单条身份切换样例，不代表提示注入全面评测通过。模型是否保持领域范围与是否能够越权调用工具，是需要分别验证的两件事。
