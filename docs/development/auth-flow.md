## 2. 注册与验证码

验证码内部生成6位随机数字，Redis仅保存用途/请求/邮箱绑定的HMAC及失败次数。重发替换当前记录，旧请求不能兑换；错误次数达到上限则失效。成功校验与创建随机注册凭证在同一Lua执行中完成，之后消费验证码。验证码兑换的响应丢失时不补发已生成凭证，按设计重新申请验证码。

注册凭证不是登录凭据。注册先检查已有数据库消费结果；新注册在同一事务创建用户和消费记录，提交后才能返回201。相同、仍有效凭证的成功重试返回200，不重新散列或覆盖密码、不自动登录。唯一约束冲突后在新事务查询该凭证的既有结果；不能把其他凭证或其他账号的冲突说成成功。

Redis注册记录在数据库提交后才尽力清理；清理失败不撤销账号。记录已清理但响应丢失时，通过数据库摘要与原有效期恢复已有结果。Redis与PostgreSQL不假设共同提交，数据库异常返回503，不主动再次创建用户来掩盖结果不明。

**当前缺口**：`POST /auth/email-verifications`尚无加密短期邮件载荷、持久任务及Outbox，始终返回503 `EMAIL_SERVICE_UNAVAILABLE`。内部验证码生成函数不等于邮件已安排，不被此HTTP入口调用；没有公开返回验证码、日志抄码或测试模式旁路。后续须先实现邮件协调与投递，再允许返回202。因此本轮的注册正常路径仅通过显式模拟夹具验证，用户还不能从网页完整注册。

## 3. 会话、CSRF与昵称

- `GET /auth/csrf`建立或复用预登录会话，返回与该会话绑定的CSRF令牌；响应不含原始会话ID。令牌由服务端密钥与会话ID分域HMAC产生，不是仅检查请求头存在。
- 会话ID为32字节随机值，浏览器仅以HttpOnly、SameSite=Lax、host-only、`Path=/api/v1` Cookie持有；Redis键使用HMAC，不存原始Cookie值。部署HTTPS时启用Secure；当前HTTP例外只用于回环地址开发。
- 修改请求必须同时通过明确Origin白名单与`X-CSRF-Token`校验。缺Origin、`null`和相似恶意域名拒绝。不开放CORS凭证读取，不信任调用方自行填写的转发IP；当前Uvicorn明确关闭proxy headers。
- 登录验证成功后重新检查账号有效性，并在Redis中原子建立新会话、撤销旧会话。CSRF随会话变化，前端需再次获取；退出删除服务端记录并清Cookie。Cookie尚在但Redis记录过期仍然拒绝，绝不降级为免认证。
- 每次本人资料访问重新查询有效账号；停用账号不能凭旧Cookie继续访问。不同的未知账号、错误密码、停用账号返回相同登录错误；未知账号仍进行密码散列验证，但不宣称完整恒定时耗或已通过账号枚举专项测试。
- 密码工作转入AnyIO线程，单个API进程最多2个并行密码任务，不直接阻塞异步事件循环；没有因此承诺高QPS或全请求队列有界。
- 本人昵称保存沿用数据库版本条件与首次完成时间保留。`completed_user`为后续剧组API提供403 `PROFILE_INCOMPLETE`门槛，但不替代剧组/对象授权及写入事务的最终校验；目前尚无剧组API。

## 4. API状态

以下路径均位于`/api/v1`。账号模块默认关闭时返回503；正常参数错误、超大请求等仍按真实HTTP状态码拒绝。OpenAPI补充标准错误体。

| 路径 | 当前行为 |
|---|---|
| `GET /auth/csrf` | 已实现，返回令牌并按需设置预登录Cookie，禁止缓存 |
| `POST /auth/email-verifications` | 尚未接邮件，明确503，不返回202或验证码 |
| `POST /auth/email-verifications/verify` | 已实现原子兑换；当前无真实邮件申请来源 |
| `POST /auth/register` | 已实现注册事务及201/200重试结果；不自动登录 |
| `POST /auth/login` | 已实现，返回本人基本资料并轮换Cookie |
| `POST /auth/logout` | 有效会话退出204，删除服务端记录并清Cookie |
| `GET /users/me` | 已实现，未登录/失效401，账号信息按白名单输出 |
| `PATCH /users/me/profile` | 已实现，版本冲突409、格式错误422、来源或CSRF失败403 |

认证响应禁止缓存；错误不含密码、验证码、连接URL或SQL。正文上限按实际字节数计，不能用分块传输绕过；有正文的认证修改只接受`application/json`。

## 5. 初始参数与启用方式

| 参数 | 本地初值 |
|---|---|
| 验证码有效期／重发间隔／单请求错误上限 | 300秒／60秒／5次 |
| 注册凭证有效期 | 300秒 |
| 预登录／登录会话TTL | 900秒／28800秒，服务端固定到期，不滑动续期 |
| 登录限流（60秒窗口） | 每IP20次、每规范化邮箱10次 |
| 验证限流（60秒窗口） | 每IP30次、每规范化邮箱10次 |
| 注册限流（60秒窗口） | 每IP10次、每凭证5次 |
| 内部申请验证码限流（60秒窗口） | 每IP10次、每邮箱5次，另有60秒重发间隔 |
| CSRF获取限流 | 每IP每60秒60次 |

这些是开发初始选择，不是性能或安全验收阈值。计数采用单机Redis短窗口Lua策略；不支持Redis Cluster多槽脚本，也未实现自适应风控。Redis变更命令关闭客户端自动重试，避免结果不明时透明重放；用户重复请求仍按各业务规则处理。

需在已有根目录`.env`中**手动合并**`AUTH_ENABLED=true`与私有随机`AUTH_SECRET`，并配置PostgreSQL、Redis及明确的`AUTH_ALLOWED_ORIGINS` JSON数组。不要覆盖已有Qwen密钥，不用公开测试密钥，不把密钥传给前端。`AUTH_SECRET`需32—256字节，随机生成并妥善保存；未配置时启用认证会阻止启动，而不是自动生成不稳定默认值。

Compose读取的是显式选择的`deploy/.env`，不是根目录配置；需同样合并私有认证密钥并使用`--env-file deploy/.env`。仓库的`deploy/.env.example`仍默认关闭认证。当前Compose只绑定本机回环地址，不用于公网。

新增配置后重启API；更换认证密钥并重启会使旧会话键不可访问，旧验证码记录也不能继续使用，旧记录按原TTL清理。当前没有多密钥轮换窗口设计。启用认证也不会启用尚未实现的邮件任务或Diane。
