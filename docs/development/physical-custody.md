# 实物借出与分次归还

迁移头`0010_custody`，新增`resource_checkouts`和`resource_returns`。资源详情已接入经办授权、借出、分次归还、权限过滤列表和逾期展示，并接入预约取消、资源减量和离组责任保护。本轮不处理Docker、不运行真实数据库迁移、不调用模型；尚未完成真实环境验收。

## 数量与权限

只有设备和道具可借出，场地不产生借还记录。实际借用人首期固定为预约申请人，不接受客户端任意指定他人；日后开放代领须补独立责任及知情确认规则。当前申请人必须在组且入组时间与原申请一致。

借出要求有效的`resource.checkout`及本资源的当前入组范围，归还要求`resource.return`及对应范围。负责人、制片和管理员身份本身不带经办权限。只读列表向经办人开放本资源记录，其他成员只能看本人本次入组借用记录；管理员不例外。

累计借出不超过预约批准数量，归还不会重置该预约的累计借出额度。实际在外数量为所有借出量减已归还量，不因预计时间或预约到期变为0。借出时还要检查资源总量减实际在外量，避免前一次逾期未还导致重复出库。

借出只在已批准且尚未结束的预约区间内，资源必须可用；预计归还时间位于实际借出时间与预约结束之间。实际经办人、借出及归还时间均由后端记录。归还允许资源已停用、预约已过期或借用人失效，但仍重新检查经办人权限和范围，不能超量归还。

`returned_quantity`是同事务维护的汇总，每次归还另写不可覆盖的流水。逾期／未归还／已归还由数量和数据库当前时间计算，客户端不能直接设置状态。当前只支持完好数量归还；损坏、丢失、赔偿和责任转移不通过“标为已归还”处理，后续另设计。

## HTTP接口

统一前缀`/api/v1/crews/{crew_id}`，沿用登录、昵称门禁、Origin／CSRF、限流、16 KiB JSON与禁止缓存规则。

| 方法与路径 | 输入与响应 |
|---|---|
| PUT `/resources/{resource_id}/custody-authorization` | 管理员替换指定成员在本资源的借出／归还范围，返回200授权及资源／成员新版本 |
| POST `/resource-reservations/{reservation_id}/checkouts` | 预约版本、正整数`quantity`、带时区ISO `expected_return_at`，返回201借出记录 |
| POST `/resource-checkouts/{checkout_id}/returns` | 借出记录版本、正整数`quantity`、可空`note`（最多500字），返回200该借出记录的新汇总 |
| GET `/resources/{resource_id}/checkouts` | 当前有权查看的借出记录，页码1—100000、页大小1—20 |
| GET `/resource-checkouts/{checkout_id}` | 本人本次入组或有该资源经办权者读取单条借出当前状态，用于冲突后的版本核对 |

所有修改都必须带UUID `Idempotency-Key`。输入拒绝额外字段，严格整数不接受布尔／字符串。授权输入为`member_id/expected_lock_version/expected_member_lock_version/permission_codes/grant_capabilities`，代码仅允许`resource.checkout/resource.return`，空数组撤销该成员在本资源的经办范围。

`grant_capabilities`默认false，要求目标已有相应能力。明确true时才把所选业务能力的例外设为allow（可能替换deny），记录前后效果并递增成员版本。范围撤销不会撤销成员在其他资源可能需要的全局能力。该入口不改负责人、不授审批权，不是任意权限编辑器。

借出DTO包含ID、剧组／资源／预约ID、借用成员、借出／已还／未还数量、实际借出及预计归还时间、经办人、版本和计算状态，不含邮箱。归还接口返回当前借出汇总；原始归还流水暂不提供独立查询API。

错误包括`FORBIDDEN/NOT_FOUND/VERSION_CONFLICT/MEMBERSHIP_CHANGED/IDEMPOTENCY_KEY_REUSED`及`RESOURCE_TYPE_UNSUPPORTED/CHECKOUT_NOT_ALLOWED/INVALID_RETURN_TIME/PHYSICAL_CAPACITY_CONFLICT/RETURN_QUANTITY_CONFLICT/RESOURCE_NOT_RETURNED`。数据库错误由现有资源服务统一转为脱敏503。

## 一致性与现有流程保护

写锁顺序为账号 → 剧组协调锁 → 资源 → 预约 → 借出记录。借出和归还都递增预约版本，归还还递增借出版本；记录、数量汇总、审计、幂等回执和变动事件共同提交。事件仍未接入资源通知消费者，不宣称已通知用户。

同键同内容重放前检查当前入组身份及经办授权，返回原成功快照，不重复记账；不同动作／目标／正文共用同键拒绝。重放是历史回执，当前状态和逾期结果应重新查询。提交结果未知不意味着可改用新键重复记账，后续页面须冻结原请求提供显式原键恢复。

- 未归还实物阻止取消原预约，不用取消消除责任。
- 减少登记总量不得低于当前未归还总数，同时仍检查未结束预约峰值；时间占用与实物占用分开核对，不简单相加。
- 预约到期但仍有未归还物品时，申请人的资源责任继续阻止离组，并出现在现有分页责任预览中。
- 预约余量接口仍只反映时段预约，其`physical_inventory_status=not_implemented`表示该查询尚未整合实物余量，不能理解为借还账本不存在。页面整合时再升级此响应契约。
- `dependency_check_status=not_implemented`仍保留，因为拍摄计划依赖检查未接入；实物取消保护已经生效。

## 页面接入

上述前端待办现已接入`frontend/src/resources/CustodyPanel.tsx`：按条展示实际借出、已还、未还数量及借出／预计归还时间，分页不冒充全组库存统计。资源DTO的`custody_actions`由后端按当前能力和本资源范围计算，控制借出／归还入口；管理员通过独立授权入口为指定成员替换借还范围，可明确授予所选能力，两项不选并确认表示撤销范围。

借出入口位于已批准预约旁。授权借出经办人额外可读本资源的已批准预约，便于选择记录；不因此开放他人待审、拒绝或取消的申请。借还API仍实时复核时段、数量、状态和权限。借还成功后刷新当前剧组查询，使预约版本、经办权限和已还数量同步。

表单沿用先核对再提交，输入时间为北京时间，原请求键只在明确确认时发送。网络结果未知时用户明确以原内容、原键重试；业务冲突先读取当前资源、预约／借出版本，保留数量和说明再核对。停用或预约过期不隐藏合法归还入口。单条GET延续列表隐私范围，重新入组不能读取旧借用记录。

新客户端`api/custody.ts`复用同源HTTP与CSRF，使用后端契约类型；原生表单提供必填、数量和长度约束，最终业务判定在后端。本轮未新增依赖或逐字段响应校验层。前端新增6项借还交互测试，后端新增3项授权读取／入组隔离测试。资源通知、耗材、计划依赖、归还历史查询及损坏丢失处理仍待完成。
