版本：D0.3  
状态：已确认岗位默认权限、对象级限制及可授予范围；权限尚未实现，相关测试未执行。

## 1. 依据与判定顺序

对应FR-01、02、05、06、09、10，BR-01—03、08及NFR-03、09。身份以可信登录上下文为准：先验证账号、资料完成、当前在组状态，再合并岗位默认权限，应用明确允许和拒绝，最后检查对象范围、责任、版本与状态。同一权限拒绝优先于允许；无授权默认拒绝。

页面按钮只是提示；HTTP接口、Worker和Diane受控工具复用业务服务中的授权判定。延迟执行时重新校验，不沿用入队时永久授权。

## 3. 权限代码及默认授予

代码用于固定权限目录；“全体”表示基础成员默认能力，不等于全部对象访问权。对象级限制仍适用。

| 权限代码 | 默认授予 | 作用及限制 |
|---|---|---|
| `crew.read`、`member.read` | 全体 | 当前所属剧组摘要及基本成员岗位 |
| `member.invite`、`member.remove`、`member.authorize` | 管理员 | 邀请、移除及预定义授权；受末位管理员和交接保护 |
| `task.read`、`task.work`、`task.review` | 全体 | 本人发布、负责、协作或确认范围；工作只限负责人，审核只限确认人 |
| `task.manage` | 导演、制片 | 查看、分配、调整及取消剧组筹备任务，不自动代提交或验收 |
| `script.read`、`script.edit`、`script.confirm` | 导演、编剧 | 剧本维护、正文核对和工作版本切换，不等于场戏或分镜审核 |
| `scene.read`、`scene.edit`、`storyboard.read`、`storyboard.edit` | 导演、编剧 | 创作资料查看、草稿编辑及送审 |
| `scene.review`、`storyboard.review` | 导演 | 审核对应创作资料 |
| `availability.self` | 全体 | 本人档期读取和维护，不开放代改 |
| `availability.read_all` | 导演、制片 | 当前剧组排期所需档期汇总，不扩展到其他剧组 |
| `resource.read`、`reservation.apply` | 全体 | 资源目录、可用性及本人申请；不含他人全部借用资料 |
| `resource.manage` | 制片 | 资源与场地资料维护，可明确授权工作人员 |
| `reservation.review` | 按需授权 | 同时为当前资源负责人方可审批，不随任意岗位自动获得 |
| `resource.checkout`、`resource.return`、`stock.manage` | 按需授权 | 对应资源范围经办借出、归还及耗材流水，不因可读资源自动获得 |
| `plan.read_related`、`call_sheet.read_related` | 全体 | 本人参与安排或作为接收人的对应内容，不默认读取无关草稿 |
| `plan.read_all` | 导演、制片 | 剧组计划查看；完整人员档期仍需相应权限 |
| `plan.edit`、`plan.publish` | 制片 | 编辑及发布，独立检查版本、冲突和风险确认 |
| `call_sheet.edit`、`call_sheet.review`、`call_sheet.publish` | 制片 | 通告编辑、审核、发布；各动作分别校验 |
| `call_sheet.export` | 制片 | 导出有权访问的具体版本，不因接收通告自动获得额外导出权 |
| `notification.read_self`、`notification.acknowledge_self` | 全体 | 仅本人通知读取和知悉 |

文件、后台任务及提案不设“猜到ID即可访问”的通用权限；按其所关联业务授权。通告接收集合见D03第19.3节，资源范围见D03第12.3节及D05第25.1节；范围不替代权限代码，制片资料维护例外不扩张成审批和经办特权。

## 4. 管理员可授予范围

管理员可授予本章预定义岗位和允许委派的业务权限，不要求自己先具有该业务执行权。“可授予”与“可执行”分开：管理员可以授予制片发布权，但自己仍不得直接发布，除非明确兼任或获业务授权。

业务例外授权只允许选择固定目录中的业务代码，不接受自定义代码、通配符、任意工具或平台级权限。管理员组织权限通过`admin`岗位授予或撤销，不通过普通`member_permission_overrides`伪造；禁止使用例外授权部分改写管理员的组织管理能力，以免绕过末位有效管理员保护。

授予或移除`admin`也须当前管理员明确提交，展示差异、责任及关联影响，事务内检查至少一名有效管理员，记录审计；成员记录版本及剧组协调锁共同防并发撤权。创建者仅在创建时取得管理员岗位，不因`created_by`享有永久特权。需要制片能力时明确兼任。

## 5. 对象级接口检查点

| 接口范围 | 权限及额外检查 |
|---|---|
| D05第6、21节：邀请、成员及岗位修改 | 对应组织权限；剧组、在组、成员版本、末位管理员及责任交接；岗位数组和覆盖代码白名单 |
| D05第7节：任务 | 管理接口需`task.manage`；开始及提交需`task.work`且为负责人；验收需`task.review`且为当前确认人 |
| D05第8—11节：文件和创作 | 上传及访问对应资料权限；同组、来源、草稿状态；确认正文与审核创作分开 |
| D05第12节：档期 | 修改必须是本人；汇总需`availability.read_all`；任何业务授权不能豁免本人维护边界 |
| D05第13—15节：资源 | 资料维护、预约申请、批准、借还和库存分别授权；批准同时检查当前负责人，经办检查资源范围 |
| D05第16节：计划 | 相关或全组读取分别过滤；编辑需`plan.edit`，发布需`plan.publish`，人工确认不绕过冲突 |
| D05第17节：通告 | 编辑、审核、发布及导出分别校验；读取按接收关系或业务权限；来源和版本仍有效 |
| D05第18节：通知 | 本人读取及知悉；回执需对应责任或明确权限，不能替人确认 |
| D05第19节：Diane | `diane.use`加本人对话；工具再检查实际业务权限；确认提案按真实动作，不设置万能`agent.approve` |
| D05第20节：任务结果 | 当前成员有目标业务查看权，不直接暴露Celery结果、内部负载或私有路径 |

资源负责人为对象关系，不增加同名岗位。指定负责人时须具备对应审批权限，否则拒绝并提示先明确授权；借还和库存经办必须明确授权到资源范围，不从负责人名称推导无限业务权。任意权限变化在延迟执行时重新检查。

## 6. Diane私有对话与他人审批

首期对话仅创建者可访问；查看提案与批准执行也是不同权限。需要他人确认时按D03第23.1节及D05第25.2节分发，独立入口只提供必要变更、依据和影响，不开放整段私有聊天及其他工具输出。未分发的他人无权读取，被分发者仍须有实际动作权限；不是会签，任一合格确认人一次决定即可，决定后不再改集合。

Diane不代维护任何成员档期或点击知悉；原有`availability.self`与通知本人接口仍由用户通过普通页面操作，不注册为Agent写工具。预约申请提案只产生待审申请，不能借此批准。用户对目标无权时Diane同样无权，模型不能声明新权限。

## 7. 测试与缺口

回归TG-F01、F02、F05、F06、F10、B01、B03、B08及N03、N09。新增重点验证：仅管理员不能业务发布但可授予制片岗位；兼任权限合并及明确拒绝；非资源负责人即使有批准代码也被拒绝；有负责人关系但缺权限不能任职；其他管理员不能查看私人对话；他人提案确认页面不泄露聊天；Diane不能代改档期或代确认知悉。

本章默认岗位、可授予范围、资源范围和提案分发已有规则及字段对应，不等于GAP-02整体关闭；其余接口契约、关联索引、提醒及模板限制继续细化，测试尚未执行。
