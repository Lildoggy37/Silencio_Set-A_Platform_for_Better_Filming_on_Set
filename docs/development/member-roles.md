# 成员岗位管理

阶段记录：本页保留岗位管理阶段的40项前端、260项后端测试快照及当时`0004_crews`迁移头。后续邀请链路已实现，最新状态见[邀请链路说明](invitations.md)。岗位管理对应FR-01、BR-01—03、D03第3/4/27节、D05第6节及D10权限矩阵，不增加业务需求。

## 2. 接口

`PUT /api/v1/crews/{crew_id}/members/{member_id}/roles`。

输入`role_codes`为固定8类岗位中的不重复数组，允许空数组或兼任；`expected_lock_version`为1—2147483647的严格整数。拒绝未知代码、重复岗位及额外操作者字段。成功200返回成员标识、显示名、在组状态、岗位和新版本；不返回邮箱或账号私有字段。

错误包括：无组织权限403、目标不在本剧组或无访问身份的隐藏404、非在组成员`409 MEMBER_INACTIVE`、版本冲突`409 VERSION_CONFLICT`、版本耗尽`409 VERSION_EXHAUSTED`、末位管理员`409 LAST_ADMIN_REQUIRED`。沿用来源/CSRF、16KiB实际请求字节限制及禁缓存；PUT与创建共用每IP/用户窗口10次的写预算，不误用读取预算。

## 3. 事务与并发

一次岗位替换使用同一数据库事务：

1. 对当前有效账号取得共享锁并重新检查昵称完成状态，随后对所属剧组取得`FOR UPDATE`协调锁。
2. 取得剧组锁后重新读取操作者在组身份、岗位和覆盖权限，检查`member.authorize`。不使用请求开始时的永久权限快照；等待期间已被撤权的管理员不能继续操作。
3. 锁定同剧组目标成员，检查状态和`expected_lock_version`。取消管理员时，仅统计本组其他在组成员中、账号有效且持有管理员岗位的人员；退出、移除、停用账号及其他剧组均不计入。
4. 在协调锁下保证至少保留一名有效管理员，替换岗位集合，递增成员共享版本，并写入岗位前后差异和实际操作者审计；提交成功后返回。

岗位、成员状态及例外授权后续写入都必须复用剧组协调锁与成员版本，不能各自检查后独立提交。未来全局账号停用还须参与相关剧组的管理员保护协调；当前没有开放停用账号接口。本批没有实现退出、移除及业务责任交接，也不能据此宣称它们已受完整保护。

创建者无永久管理权；导演或制片不能凭业务岗位修改其他成员岗位。岗位变更不清除既有业务例外授权；管理员的组织权限仍只能来自`admin`岗位。空岗位成员保留基础成员能力。

## 4. 前端行为

当前剧组具有`member.authorize`时，在成员目录显示管理入口。先选择岗位，再展示当前与拟变更集合；涉及管理员变化时说明组织权限与失去自身管理入口的影响，最后明确确认。后端每次执行仍重查权限。

同步锁防连点，写请求不自动重试。版本冲突、断连、异常响应或服务错误后保留选择，先明确读取当前岗位，再重新核对后提交；读取本身不会补发写入。目标不在当前分页时要求关闭后重新选择，不冒称目标一定已退出。

响应必须确认同一成员、恰好递增的版本及提交的岗位集合。成功后刷新成员、剧组摘要及本人有效权限；本人被取消管理员后移除管理入口。成员列表刷新失败不把已确认写入说成失败，也不自动重放。岗位替换目前没有独立幂等回执，响应未知时不能承诺严格只执行一次；旧版本重提会冲突，必须读取当前状态。
