# Diane：人工确认创建任务

本批实现 FR-10 的首个写入闭环：输入要求 → 模型拟定普通任务 → 保存私有提案 → 人工审阅 → 确认后原子创建整批任务。迁移头为 `0026_task_proposals`。已有只读查询工具保持只读；模型没有直接创建正式任务的工具。

## 用户操作与范围

有 `task.manage` 权限的成员在 Diane 中选择“拟定任务”，输入要求，明确选择负责人和共同截止时间。模型只拟定 1—5 项标题与说明，负责人和截止时间由服务器绑定用户表单值，默认无需逐项验收。确认前展示全部任务、负责人姓名、截止时间和完成方式。

提案保存于 PostgreSQL，30 分钟有效，可在“最近的提案”查看本人最近 10 份。放弃不创建任务；确认后显示真实任务标识并可跳转查看。需要调整内容时重新拟定一份独立提案；本批不提供原地修改已保存提案。不同提案不会按内容自动去重，用户确认的是指定提案的指定版本。

本批仅支持发起人本人确认，仍须当前具备任务管理权限；不能查看或确认他人私有提案。未实现跨人分发、多候选审阅、不同负责人／截止时间的混合批次、重要任务验收设置、通用工具提案、任务调整／取消／资源预约提案、异步执行或跨业务补偿。

## 核心代码

- `diane/service.py`：先检查明确选择的成员与截止时间，再调用只有 `draft_tasks` 的模型循环。工具只在内存收集草稿；模型完成后复验并保存提案。生成阶段不创建任务，不查询额外剧组资料。
- `diane/proposals.py`：按当前剧组、用户、成员 ID 与精确入组时间限定提案。生成时保存负责人等相关成员的 ID、入组时间及版本。确认时检查权限、原提案版本、有效期、成员快照、当前分配资格及截止时间。
- `tasks/repository.py`：原任务写逻辑抽取为 `mutate_in_session`，原页面写接口仍由自己的事务调用它。`TaskService.create_in_transaction` 让确认流程复用相同任务规则及审计／事件／回执，不另写一套创建逻辑。

确认事务按既有剧组协调锁 → 提案行锁的顺序执行。每项任务使用提案 UUID 与索引派生的稳定 UUID 幂等键。任务、协作成员、任务回执、变动事件、审计与提案完成状态同一事务提交；任意一项失败全部回滚，提案仍待确认，不产生部分成功。

重复或并发的相同决定返回已有任务标识，不再次创建；相反决定或不符版本返回 409。已完成的提案不会因重复确认再次检查过去的截止时间并新建一组任务。重放前仍检查当前权限和原入组身份，离组重新加入不能恢复旧提案访问权。

网络结果未知时页面冻结原决定，支持读取最新结果或显式重试同一提案／版本／决定；不重新调用模型。确认及重试不计模型 tokens。错误或来源变化时重新拟定，不默认豁免业务检查。

## 接口

前缀 `/api/v1/crews/{crew_id}/diane`：

| 接口 | 内容 |
|---|---|
| `POST /task-proposals/draft` | `question`（最多 4000 字）、`owner_member_id`、带时区 `due_at`；返回模型结果及可选提案，澄清或模型失败时不保存空提案 |
| `GET /task-proposals` | 当前成员本人最近 10 份，包括固定任务内容、成员名称、版本、状态、有效期和实际任务标识 |
| `POST /task-proposals/{id}/decisions` | `expected_lock_version`、`decision=accept/reject`，不接收替换任务内容；重复相同决定可恢复结果 |

沿用登录、昵称、Origin／CSRF、请求大小与不缓存策略。生成共享原模型调用频率及并发限制；决定单独限频。模型配置失效时不影响普通任务接口。已保存提案的决定不需要再次调用模型。

数据库记录私有提案内容、成员快照、生成结果和用量概况，以及确认后的任务标识。此为任务提案记录，不是通用会话持久化或 LangGraph 检查点。查询状态接口的 `mode` 更新为 `queries_and_task_proposals`；生成普通任务无需另行执行任务验收。

## 验证与设计差异

- 真实 PostgreSQL、新隔离数据库：模型模拟生成两项提案但正式任务数为 0；两个并发确认返回同一组两个任务；其他有管理权限的成员仍无法读取／确认；错误版本和无 CSRF 被拒绝。
- 第二项执行前注入业务校验失败，第一项也回滚，任务总数不变；解除失败后可再次确认且仅创建一批。拒绝可重复，过期和成员版本变化阻止执行。
- 原任务与 Agent 相关 55 项检查通过；前端提案相关 3 项与原查询侧栏 3 项通过；构建通过。
- Edge 使用模拟提案／决定响应检查审阅和创建反馈，确认前没有决定请求，确认后仅一次请求；390px 页面与侧栏均无横向溢出，无页面脚本错误。未在原试用剧组自动创建测试任务，未进行额外的真实模型提案调用。
- 现有试用数据库已做本地备份后升级，原剧组、任务、资源及预约记录数量保持一致。

相比完整设计中的 `confirmed → executing → completed` 通用异步提案，本批在一个 PostgreSQL 事务中同步确认与执行，采用 `pending → completed/rejected`，不虚构排队或执行中状态。原设计多操作部分成功机制暂不适用于这个有界任务批次，任务批次采用全有或全无。上述差异对应 FR-10／AC-10；对其他业务提案和队列执行的设计仍属后续范围。
