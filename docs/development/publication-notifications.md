# 排期与通告的站内通知、本人知悉

本批将正式排期发布与通告生命周期事件接入既有通知中心，迁移头为`0018_publication_notices`。前期[任务通知与交接](notifications-and-handover.md)保留为阶段记录；本页说明当前多来源通知契约。真实数据库迁移及消费进程尚未运行。

## 事件消费

继续使用`python -m silencio_set.notifications.consumer`，无需新增Worker。每轮按发生时间从任务、排期、通告的待处理事件中取至多一项，先锁剧组，再重查并锁定事件。选择当前有效账号／成员，重查通知与业务来源权限，创建通知和接收记录，最后更新事件消费标记并共同提交。数据库错误回滚，由既有循环稍后重试；不在事务中调用SMTP、模型或Broker。

三类事件均增加待处理查询索引。通知仍唯一关联原事件，新来源通过同剧组复合外键关联；数据库约束确保任务事件、排期事件和通告事件恰好有一个非空。同一事件不会形成多份通知；重复消费不会追加接收人或重置已读／知悉时间。

| 来源 | 接收范围与知悉规则 |
|---|---|
| 正式排期发布 | 新旧版本参与人员；当前入组身份必须匹配快照。新版参与人员需知悉，已从新版移除者收到调整提醒，不要求确认新版 |
| 通告发布 | 审核并发布的接收集合，本次入组身份一致者；需本人知悉 |
| 通告待复核／撤回／被替代 | 原发布接收集合，仅提醒状态变化，不要求确认失效安排 |
| 筹备任务变更 | 保持既有当前任务关系与权限规则 |

有候选记录不等于能投递：离组、重新入组或失去通知／来源读取权限时不会生成本人接收记录。排期中被移除的成员仍可收到固定变更提醒，但没有完整排期权限及当前参与关系时不返回计划名称，不开放新版内容预览。通告相关读取额外要求对应版本的发布接收记录；编辑／审核／发布人员仍只看到实际发给本人的通知。

## 读取与确认

既有列表、详情、已读与知悉四个接口路径不变。通知列表一次查询关联三类来源并分页，不逐条读取完整安排或剧本。除了本人接收记录、有效成员和入组身份匹配，还实时检查来源权限。

当前响应以通用字段取代旧`task_id/task_title`：

| 字段 | 含义 |
|---|---|
| source_type | task／plan／call_sheet |
| source_id | 任务ID、排期版本ID或通告版本ID；仅作为入口，具体内容接口仍独立鉴权 |
| object_title | 当前可展示的对象名称；无法查看新版排期的接收人仅显示“拍摄安排” |
| object_version | 通知依据：任务锁版本、排期版本号或通告事件锁版本 |
| current_object_version | 对应当前版本，可能为空；相同数字不能单独证明安排有效 |
| is_current | 当前指针、版本与来源有效状态共同判定 |
| source_status | current／updated／review_required／superseded／withdrawn |
| can_open_source | 是否可进入通知对应来源内容 |

通知ID、事件类型、固定标题／摘要、发生时间、是否需知悉及本人已读／知悉时间继续返回，不包含邮箱或其他接收人的资料。

已读与知悉保持分开；GET及来源预览均不自动标记已读。知悉只接受本人操作和通知依据版本，不代替审批、到场、任务完成或验收。排期不再是当前正式版本或有待复核标记时，旧通知不能新增知悉。通告还须事件为发布、锁版本一致、当前指针指向本版本、通告有效且来源排期仍当前有效；撤回、替代和待复核均拒绝新确认。

首次知悉同时记录已读；重复操作保留原时间。已有历史确认可在重查当前访问权后返回原结果，不迁移到新版。`needs_acknowledgement`筛选按同样的来源有效条件计算，失效通知不进入待知悉列表。

## 页面

通知中心统一显示任务、排期和通告及其状态。任务仍跳转工作台，排期和通告可在只读窗口查看通知对应版本；后端继续控制本人范围与历史权限。预览失败会隐藏内容并显示错误，不把通知摘要当成完整安排。知悉前仍单独核对并明确提交。

通告发布界面说明发布与知悉的区别。当前已接入制片／获授权人员查看排期与通告发布通知的回执页面，区分待处理、通知已生成、未生成及已读／知悉，见[撤回与回执说明](plan-withdrawal-and-receipts.md)；通知未接入外部邮件、浏览器推送或短信。排期来源待复核会阻止原通知继续确认，但本批未新增独立的排期待复核事件类型。

## 迁移与验证

迁移保留任务通知数据，将旧`source_event_id`改为可空并增加两类来源列、唯一键、同剧组外键及恰一来源约束。回退先恢复任务来源非空约束；已有排期／通告通知时回退会失败，事务不会先删除这些记录，不以清空业务数据完成降级。

相关后端101项分批通过：新多来源通知19、既有任务通知26、通告33、排期发布23。前端通知接口、通知中心与通告页面21项通过；TypeScript／Vite构建通过。覆盖新旧接收集合、权限／入组身份、通告生命周期、回执版本、事务提交失败、失效保护、统一查询与离线迁移；未重复全量测试。

消费者需要在真实迁移后显式运行。发布返回的`pending_dispatch`仍只代表业务事件已保存；不代表已生成站内通知、成员已读或知悉。真实PostgreSQL锁竞争、进程恢复、浏览器视觉及性能验收仍待完成。本批未处理Docker，未访问真实邮箱或模型API。

后续`0022_plan_withdrawal`新增`plan.withdrawn`取消通知，只提醒原参与人、不要求确认；原发布通知按撤回状态失效。撤回后不会恢复上一正式版本。
