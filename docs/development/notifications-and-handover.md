# 站内通知与任务交接清单

当前已实现：任务变更事件的站内通知消费、本人通知分页/筛选/详情、已读与明确知悉、旧版本保护、任务责任清单及处理跳转。本模块迁移为`0007_notifications`；最新迁移头`0008_availability`见[档期说明](availability.md)。邮件仍沿用原有独立链路；本模块不发送外部消息，也不调用模型。

真实数据库迁移、并发消费及浏览器视觉验收尚未执行；代码和模拟测试不代表已在实际邮箱、数据库或容器中运行。预约、拍摄安排及通告的通知与交接继续随对应模块接入。

## 1. 核心流程

任务创建、调整、开始、提交、验收和取消仍在原业务事务保存`task_change_events`。接收候选包括新旧负责人/确认人、发布人和协作人，去重最多45名，不在任务请求中执行通知投递。

`NotificationConsumer.consume_once()`每轮处理至多一个事件：读取候选 → 锁定剧组 → 对仍待消费的事件加锁重查 → 查询当前任务及有效成员权限 → 创建通知及接收记录 → 标记事件已消费 → 共同提交。与任务写入、授权变更和离组使用同一剧组协调锁，不在持锁期间调用Broker或SMTP。

源事件唯一约束、事件业务键与接收人复合主键共同防重复。事务中断不形成半份通知；提交结果未知后下一轮检查源事件状态，不重新生成通知或重置回执。已存在通知的恢复路径只补消费标记，不追加接收人。格式非法或未知类型事件标记`failed`，普通数据库异常回滚并由循环稍后重试；错误日志仅记录异常类型。

候选人须仍在组、账号有效，具备通知读取和当前任务读取资格；当前入组时间必须不晚于事件发生时间。接收表保存入组时间快照，后续查询要求与当前成员`joined_at`一致，因此离组后重新加入不恢复旧通知。曾是接收人不能绕过当前任务可见范围。

通知标题和摘要采用固定模板；任务标题在读取时按当前权限获取，不复制成果说明或验收原文。通知详情可打开当前任务，旧版本明确标注“任务已有更新”。

## 2. 已读与知悉规则

- GET列表/详情无标记副作用；页面由本人明确“标记已读”。
- 创建/调整通知对当前负责人及确认人要求知悉；提交通知对当前确认人要求知悉。其他接收人或事件一般只读。
- “确认知悉”先展示说明，再明确提交；要求当前`notification.acknowledge_self`权限及通知所引用版本，不替代开始、成果提交或验收。
- 已读和知悉分别记录。首次知悉会同时记录已读，重复操作保留原时间，不重复写成功审计。
- 未知悉的旧任务版本返回409 `NOTIFICATION_OUTDATED`，不能替代新版本知悉。已确认的旧版本可在当前仍有访问权时恢复原确认结果，历史时间不迁移到新版。
- 未送达、打开通知、已读、知悉、完成任务是不同状态，界面不混用。

## 3. HTTP与数据

统一前缀`/api/v1/crews/{crew_id}`，沿用登录/昵称、Origin/CSRF、JSON体上限和无缓存响应。列表页码1—100000、页大小1—100，界面固定20；通知读每窗口每IP/用户各120次，回执写各30次。

| 方法与路径 | 输入及结果 |
|---|---|
| GET `/notifications` | `page/page_size/unread/needs_acknowledgement`可选；仅本人当前可访问通知 |
| GET `/notifications/{id}` | 本人详情；缺失/跨组/他人/当前失权隐藏404 |
| POST `/notifications/{id}/read` | 空JSON对象`{}`；返回本人已有或新增已读时间 |
| POST `/notifications/{id}/acknowledge` | 严格正整数`object_version`；返回本人知悉及已读时间 |
| GET `/members/{id}/exit-responsibilities` | 分页；本人或具备`member.remove`者可查询目标 |

通知返回白名单：通知ID、事件类型、固定标题/摘要、时间、任务ID及当前标题、引用/当前版本、是否当前、是否需要知悉、本人已读/确认时间；无邮箱和其他接收人列表。确认不需要的通知409 `CONFIRMATION_NOT_REQUIRED`，引用版本不符409 `VERSION_CONFLICT`。首期未提供其他成员回执管理列表。

`notifications`按`source_event_id`唯一，通过同组复合外键关联任务事件，对象和版本由源事件派生；`UNIQUE(crew_id,event_key)`及`UNIQUE(crew_id,id)`支持去重与接收外键。`notification_recipients`以剧组/通知/成员为复合主键，保存`membership_joined_at`、是否需确认及三个时间字段，约束确认必须已读且确认时间不早于阅读时间。成员和通知外键均限制同组，历史不级联删除。

## 4. 交接清单与页面

清单在剧组协调锁内计算，返回目标成员版本、`items/total/blocking_total/restricted_total/page/page_size`。`total`仅统计有权查看的任务，`blocking_total`为全部未完成负责人/确认人责任，`restricted_total`为无权查看部分；隐藏部分不返回任务ID、标题或日期。

离组弹窗自动检查并可手动刷新；检查中、失败或有阻断时禁用确认，不能把故障当成零责任。列表按权限展示任务及本人责任类型，点击“处理任务”关闭离组弹窗并进入当前任务详情；受限事项仅提示数量和联系有权人员。待处理/进行中可调整负责人及确认人，待确认先验收或取消。

清单是预览。最终退出/移除仍重检成员版本、最后管理员及责任，不能凭旧预览放行；没有任务责任也不表示所有离组条件均满足。预约与安排检查尚待对应模块实现。

## 5. 本地运行与验证

先迁移，再显式启动消费者。后端本机方式：

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m silencio_set.notifications.consumer
# 仅处理至多一个事件，便于联调
.\.venv\Scripts\python.exe -m silencio_set.notifications.consumer --once
```

运行需要已配置数据库URL，配置按[本地开发说明](local-development.md)提供，勿覆盖真实`.env`。Compose新增`notifications`可选profile及`notification-consumer`服务；服务仅依赖PostgreSQL。消费者采用短事务轮询，无事件时每秒检查一次，故障不会使API业务事务声称通知已送达。当前没有自动清理/重新投递失败事件的管理界面。

后端测试覆盖消费事务、去重、非法事件、当前权限、入组时间绑定查询、回执版本和重放、CSRF/来源、同组外键/离线迁移及受限任务清单。前端验证已读/知悉分离、旧版拒绝、失权隐藏内容、清单阻断和处理跳转。真实PostgreSQL锁竞争、实际进程恢复、长时间运行及浏览器布局仍待联调。
