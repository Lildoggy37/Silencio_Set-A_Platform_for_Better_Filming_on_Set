# Silencio Set 项目介绍稿

适用于课程答辩或项目演示，按正常语速约 7—8 分钟。下文可以直接口述；演示样例均为虚构资料。

大家好，我介绍的项目叫 Silencio Set，中文名是“寂静片场”，是一个面向学生剧组的 Web 协作与拍摄前期准备平台。它希望解决的是：在经费有限、成员兼职参与的情况下，怎样把拍摄前的人员、资源和创作准备组织起来，让大家到达片场后清楚自己要做什么。

Silencio 取自大卫·林奇电影《穆赫兰道》中的 Club Silencio，Set 则指片场。“寂静”也有一层引申含义：当分工不清、安排反复时，片场很容易充满催促、抱怨和争论。我希望通过更清楚的筹备，减少这些沟通噪声，让大家把注意力放回拍摄与创作。

这个选题来自我在小红书发帖，以及与学生剧组交流后归纳的问题。这些属于初步的定性反馈，主要集中在三个方面。

首先是资源有限，状态又不透明。摄影机、灯光、收音设备往往需要借用，如果不知道谁在使用、什么时候归还，拍摄安排就很难落实。其次是管理依赖人情。成员通常是来帮忙的同学朋友，导演难以一直催促，任务也容易停留在群里的一句话。最后是前期准备不足：分镜和通告没有提前确定，勘景遗漏现场条件，或者大家对画面效果理解不同，到了现场才讨论，甚至为一个镜头消耗大量时间，影响整天的进度。

这些问题并不都能靠软件解决。平台无法增加预算、提供专业收音设备，也不能替代导演作出艺术判断。因此，我把重点放在能够通过信息组织改善的部分：明确责任、协调已有资源、统一筹备资料，并提前检查拍摄安排。

由此，我提出了四组核心需求。

第一组是明确“谁负责什么”。平台允许创建剧组、邀请成员，并分配导演、制片、编剧、摄影等岗位。同一个人可以兼任多个岗位。任务具有负责人、截止时间和进度，成员可以提交结果。考虑到学生团队的使用成本，普通任务默认直接完成，重要任务才选择验收，避免所有事情都层层审批。

第二组是看清“什么时间、有什么资源”。成员填报个人档期，剧组登记设备、道具和场地，按时段进行预约，并记录借出、归还和耗材数量。系统会根据容量和时间判断冲突；没有登记的档期会保留为未知，不能直接当作有空。这样，制片安排拍摄时，就有了可以核对的依据。

第三组是统一“我们究竟准备拍什么”。平台支持导入 TXT、DOCX 和带文本层的 PDF 剧本，管理版本，并维护场戏、人物、资源需求和文字分镜。导演可以查看勘景照片与场地条件，让大家围绕同一份资料协作。如果剧本或相关来源发生变化，系统会提示关联内容需要复核，减少沿用旧资料的问题。目前的场戏和文字分镜由用户整理、确认，自动生成分镜属于后续扩展。

第四组是把准备落实成“可以执行的拍摄安排”。制片把场戏、时间、地点、人员和资源编排为拍摄计划，系统检查人员时间重叠、资源容量和预约占用等问题。正式发布后，可以生成每日通告，写明集合时间、地点和注意事项，导出 PDF，并查看成员的通知确认情况。草稿和正式版本分开保存，修改草稿不会直接覆盖已经通知大家的安排。

下面用当前的演示样例《末班信号》说明这些功能怎样一起使用。这是一个虚构的校园短片剧组，有七名成员、三场戏和十个文字分镜，场地主要是教学楼走廊与校园广播室。

拍摄前，制片先分配广播室钥匙确认、灯光试摆、环境底噪录制等任务。摄影和收音成员查看自己的待办，演员登记可用时间，设备按拍摄时段预约。导演则通过场戏和文字分镜确认创作准备。

目前的正式安排是 11 月 7 日下午三点集合、四点开拍，通告已经发布。在另一个计划草稿里，我故意把第二场提前，让它与第一场重叠。系统会检查出人员和资源冲突，阻止这个草稿直接成为正式安排。这个场景体现了平台的作用：把原本可能到现场才发现的问题，提前暴露在筹备阶段。

在这些基础功能之上，我加入了 Diane 智能助手。用户可以问：“下一次拍摄在哪里，什么时候集合？”或者“当前还有哪些任务没完成，分别由谁负责？”Diane 会调用当前用户有权访问的业务工具，查询实际记录后整理回答。它也支持近期对话记忆，方便连续追问；涉及当前任务、资源和排期的事实，仍需要重新查询。

对于写入操作，目前支持任务提案。用户通过提案入口指定负责人和截止时间，由 Diane 拟定任务内容，审阅后再确认创建。模型生成建议和正式修改业务数据是两个步骤；确认时，后端仍会检查权限，并避免重复创建任务。

这也是我选择 Agent 的原因：筹备信息分布在任务、资源和计划等模块中，自然语言适合帮助用户跨模块查找、整理和拟定内容。它复用平台已有的业务能力，所有基础工作也都保留普通页面入口。

实现上，前端使用 React 和 TypeScript，后端使用 FastAPI，PostgreSQL 保存业务数据、版本和操作记录，Redis 提供会话等临时状态支持，RabbitMQ 与 Celery 承担异步任务。

Diane 使用 LangChain 和 LangGraph 组织模型调用、工具执行及运行状态，通过 MCP 接入业务工具，目前接入阿里云百炼的模型兼容接口。权限由后端业务服务执行，模型不能自行决定访问哪个用户或剧组的数据。请求提交后由后台工作进程执行，前端接收进度和结果；收起聊天窗口不会取消已提交的运行，重新打开可以读取同一次请求。页面也会展示单次运行耗时和模型返回的 token 用量，方便观察成本。

与群聊、共享表格相比，这个平台的设计重点是数据之间的关联：一场戏需要哪些人和设备，这些资源是否可用，计划修改影响哪些安排，通告又对应哪个正式版本。群聊仍然适合讨论，而平台负责保存共同确认的工作状态。

目前，基础协作功能和 Diane 的查询、记忆、工具调用及受控任务提案已经接通，可以在本机浏览器中演示。现阶段尚未完成公开部署、高并发压测和真实剧组的完整试用，不能据此宣称已经提升多少效率。接下来，我希望让学生剧组完成一次实际筹备，观察哪些信息真正有用、哪些操作仍然繁琐，再决定进一步加入哪些智能辅助能力。

## 配合页面的展示顺序

1. 剧组与任务：展示《末班信号》的成员、负责人和筹备待办。
2. 资源与档期：展示设备数量、预约时段及成员可用时间。
3. 剧本与筹备：展示三场戏、文字分镜及场地条件。
4. 拍摄计划：对照正式第 1 版与存在重叠的第 2 版草稿。
5. 每日通告：展示集合信息、PDF 导出和通知确认入口。
6. Diane：询问下一次拍摄或未完成任务；时间允许时，通过任务提案入口演示拟定、审阅与确认。

## 表述边界

- 《末班信号》是虚构的演示案例，不是已完成的真实剧组试用。
- 当前支持文字分镜维护，不宣称已实现自动分镜生成、GraphRAG 或自动优化排期。
- 当前可本机运行演示，公开代码仓库不等于系统已部署到公网。
- 当前聚焦拍摄前期准备，不包含现场场记、后期素材归档或专业音频处理。
- 若介绍当前模型，可说明使用百炼提供的 `deepseek-v4.1-flash`；早期文档中的 Qwen 选型不代表当前运行配置。
